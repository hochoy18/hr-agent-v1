HR Agent Skill 机制详解

一个技能如何从 backend/skills 下的目录，变成 Agent 可调用的工具、再拆成"草稿 → 确认 → 发送"两阶段执行？本文沿着 agent_skills.py 的加载链路，结合邮件技能完整走一遍。

📦 backend / app / services 🧩 可插拔技能 🕸 LangGraph draft → send 📅 2026-11

1全景概览

app/services/agent_skills.py 不实现任何业务。它的职责只有两件事： 加载（扫描技能目录、解析清单、建模成 bundle）和分发（按 intent 找技能、按 phase 找脚本函数）。 真正的邮件逻辑在技能包自己的 scripts/email_workflow.py 里。

💡 一句话理解 skill.json 描述"这是什么意图、有哪些阶段、每阶段跑哪个函数"； SKILL.md 描述"这件事应该怎么做"，草稿阶段会把它整段注入 Prompt； scripts/*.py 提供确定性兜底与真正的副作用（比如发信）。

2.1 skill.json 机器可读

清单文件 skills/hr-agent-email/skill.json 定义了技能的全部可执行信息：

{
  "intent": "email_notification",
  "route": "/system/email-configs",
  "phases": ["draft", "send"],
  "prerequisites": ["人工确认后再发送"],
  "default_phase": "draft",
  "confirmation_action": "send_email",
  "phase_scripts": {
    "draft": "scripts/email_workflow.py:run_draft_phase",
    "send":  "scripts/email_workflow.py:run_send_phase"
  }
}
字段作用
intent技能的意图标识，也是 bundles 的 key；必须与路由识别出的 intent 一致
route前端页面路由，写进工具描述，供 Agent 回复时引用
phases阶段列表；每个阶段必须在 phase_scripts 里有对应脚本
default_phase未确认时的默认阶段；缺省回退到 phases[0]
confirmation_action确认动作名（send_email），是草稿与发送之间的约定值
prerequisites前置条件，注册为工具时展示在描述里
phase_scripts阶段 → 相对路径:函数名 的映射

2.2 SKILL.md 给 LLM 看

skills/hr-agent-email/SKILL.md 以 YAML frontmatter 开头，只解析 name 和 description agent_skills.py:143-147： 

---
name: hr-agent-email
description: 为本项目中的HR Agent生成、确认和发送HR候选人邮件。适用于撰写面试邀请、笔试通知、候选人跟进邮件，或将草稿转为已确认的发送操作。
---

frontmatter 之下是完整的工作流说明。它会以两种方式被使用：

  • 工具描述：description 进入 tool_registry，供 ReAct 路由器判断"该不该选这个工具"。
  • Prompt 上下文：整份 Markdown 由 phase.load_skill_instructions() 读出，草稿阶段原样拼进 Prompt（core.py:329-339；脚本内 email_workflow.py:52-64）。
⚠️ 不是标准 YAML 解析 parse_skill_metadata() 只按行做 key: value 切分，不认识嵌套结构、引号和转义；且要求文件严格以 ---\n 开头。Windows 换行或格式偏差会导致描述解析为空。

3.1 目录 → Dispatcher

入口是 build_default_skill_dispatcher() agent_skills.py:233：

图 2 · 加载链路：两层解析（json 清单 + md 元信息）后组装 bundle

几个实现细节：

  • 根目录是 Path(__file__).resolve().parents[2] / "skills"（agent_skills.py:235），即 backend/skills；目录不存在时返回空 Dispatcher，不抛错。
  • 只扫描一级子目录，并按名称排序；bundles 以 intent 为 key（agent_skills.py:244）。同名 intent 后加载的覆盖先加载的。
  • Dispatcher 在 AgentService.__init__ 中构建（agent_service.py:89），而 AgentService 每个请求 new 一次。因此技能目录是每次请求重新扫描的：新增技能无需重启，但也没有跨请求缓存。

3.2 跳过与边界情况

情况结果表现
skills 根目录不存在空 DispatcherAgent 正常工作，只是没有可插拔技能
skill.json 缺失 / JSON 非法该技能跳过仅 manifest 解析失败时有一条 warning
缺 intent / phases / phase_scripts该技能跳过静默，无报错
某个 phase 没有脚本定义该 phase 跳过warning，其余 phase 可用
所有 phase 都不可用该技能跳过无报错
两个技能声明同一 intent后者覆盖前者取决于目录名排序
⚠️ 排查"技能没生效" 先确认 skill.json 的 intent、phases、phase_scripts 三个字段齐全，且脚本路径相对技能目录真实存在。加载失败大多不会抛异常，只会让技能悄悄消失。

4.1 resolve_phase：这一轮跑哪个阶段

决定"草稿"还是"发送"的规则全部集中在 AgentSkillBundle.resolve_phase() agent_skills.py:94-98：

def resolve_phase(self, confirmed_requirements=None) -> str:
    action = str((confirmed_requirements or {}).get("action") or "").strip()
    if self.metadata.confirmation_action and action == self.metadata.confirmation_action and "send" in self.phases:
        return "send"
    return self.metadata.default_phase   # 通常是 draft

也就是说：确认动作名匹配 confirmation_action，且存在名为 send 的 phase，才会进入发送阶段。 注意 "send" 这个 phase 名是写死的——新技能如果想复用这套确认机制，phase 必须命名为 send。

4.2 run：执行阶段脚本

ScriptedSkillPhase.run() agent_skills.py:56-78 是技能与 Python 代码之间的桥：

module_name = f"skill_{skill_dir.name}_{phase_name}".replace("-", "_")
spec = importlib.util.spec_from_file_location(module_name, script_path)
module = importlib.util.module_from_spec(spec)
spec.loader.exec_module(module)          # 每次调用都重新执行模块

fn = getattr(module, function_name, None)
result = fn(enriched_context)
if inspect.isawaitable(result):
    result = await result
if not isinstance(result, dict):
    raise RuntimeError(...)
  • 每次运行都重新 import，不写入 sys.modules，脚本里的模块级状态不会跨调用保留。
  • 函数可以是同步或异步，但必须返回 dict。
  • 注入的 context 除调用方字段外，还会补 skill_dir、skill_markdown（整份 SKILL.md 文本）、phase_name（agent_skills.py:67-72）。
🚫 信任边界 exec_module 会执行 skills/ 下的任意 Python。技能目录必须视为受信代码，不能开放给用户上传或远程拉取。

_build_tool_registry() app/agent/chains/core.py:44 先声明内置工具（jd / resume_screening / interview_plan / exam_generate / delete…），然后把每个 skill bundle 追加进去：

于是 email_notification 和内置工具完全同权：

  • ReAct 路由候选 = tool_registry.keys() + general reasoning.py:180；工具名、描述、前置条件会自动拼进系统提示 routing_agent.py:50-56。新技能无需改路由代码，LLM 就能看见它。
  • 规则快通道另有一层：IntentService 的关键词表里有 email_notification 的触发词 intent_service.py:39，reasoning.py:120-121 还有一条兜底正则。
  • 确认回传走 match_confirmation_action()（agent_skills.py:115），按 confirmation_action 反查 bundle，不依赖意图分类。
ℹ️ 新增技能的完整清单 建目录 + 写 skill.json / SKILL.md / 脚本，核心代码不用改； 但 rule 模式下要在 IntentService 补关键词，否则只能靠 LLM 路由或确认回传进入该技能。

6.1 skill_draft：生成草稿 LLM 流式 + 脚本兜底

skill_draft_node app/agent/nodes/skill.py:26 在流式模式下调用 _stream_skill_draft_response() core.py:258：

  1. 先推 plan 事件，展示 draft / confirm / send 三步。
  2. 取 bundle.get_phase("draft")，用 load_skill_instructions() 读出整份 SKILL.md，拼成 Prompt 交给 LLM 逐字流式生成（core.py:288-295）。
  3. 如果 LLM 流式失败，降级执行 draft 脚本（core.py:296-312）；脚本内部还有 _fallback_draft() 模板兜底（email_workflow.py:7-15）。
  4. 生成完再调 _handle_skill_intent()，把已生成的文本作为 __draft_text 传进去（core.py:321-324），避免脚本再调一次 LLM。
  5. 脚本返回 email_draft + email_send_request 两个 artifact，并设 requires_confirmation: true（email_workflow.py:78-92）。

非流式路径则直接执行 draft 脚本，由脚本自己调 llm_service.generate_response()（email_workflow.py:69-75）。两条路径最终都产出同样的 artifact 结构。

6.2 确认回传：和 JD 的 interrupt 不一样

邮件技能不使用 interrupt / resume。前端把确认内容作为新消息再发一次 /agent/graph/chat，携带 confirmed_requirements frontend/src/views/agent/HRAgent.vue:1402-1412： 

{
  "action": "send_email",
  "recipient_email": "...",
  "subject": "...",
  "body": "..."
}

路由节点 resolve_intent_and_plan() 看到 confirmed_requirements 后，用 match_confirmation_action("send_email") 反查 bundle reasoning.py:58-69，命中则直接把 intent 定为 email_notification，source 标为 confirmed_skill_action。 随后 skill_draft_node 发现 confirmed_requirements 非空，直接 return {} 空过（skill.py:29-31）； 条件边 _after_skill_draft 随即放行到 skill_send（graph.py:197-202）。

6.3 skill_send：执行发送 副作用

skill_send_node app/agent/nodes/skill.py:58 再调 _handle_skill_intent()： resolve_phase() 返回 send，执行 run_send_phase（email_workflow.py:95）→ EmailSendService.send_agent_email() → 读取 backend/skills/hr-agent-email/config.txt 的 SMTP 配置发信 app/services/email_service.py:324-361 → 返回 email_send_result，requires_confirmation 变为 false。

✅ 为什么发送阶段放在脚本里 发信是确定性副作用，不需要模型"发挥"。脚本负责字段校验、SMTP 调用和错误归类（缺配置 / 地址被拒 / 成功提交），并通过 missing_fields 把可修复的问题交还前端。

8设计要点与注意事项

✅ 做得好的地方

  • 加技能约等于加目录：manifest 描述意图和阶段，SKILL.md 描述工作流，脚本实现阶段；核心代码不用改。
  • SKILL.md 是单一事实来源：既是工具描述，也是 Prompt 约束；run() 自动把全文塞进 context，脚本无需自己找路径。
  • 两阶段隔离副作用：生成与发送分开，确认动作名由 manifest 声明，不散落魔法字符串。
  • 多级兜底：LLM 流式失败 → 脚本生成；脚本失败 → 模板草稿。

⚠️ 需要留意

  • 任意代码执行：exec_module 执行技能目录中的 Python，目录必须受信。
  • phase 名写死：确认阶段必须叫 send。
  • rule 模式需补关键词：LLM 路由能自动发现新技能，规则快通道不会。
  • 每次请求全量扫描：无缓存，技能多时有磁盘开销。
  • SKILL.md 全文进 Prompt：长文档会增加草稿轮 token。
级别问题建议
安全 技能脚本以进程权限执行任意代码 严格限制 skills 目录写权限；不要把用户上传内容放进技能目录
扩展性 resolve_phase 只认 "send" 阶段名 如需多类确认阶段，可在 manifest 增加 confirmation_phase 字段
可发现性 manifest 字段缺失时技能静默消失 加载失败改为 warning 汇总或启动期校验
性能 每个请求重新扫描目录、每个 phase 重新 import 技能增多后可加进程级缓存 + 文件 mtime 失效
一致性 同名 intent 后者覆盖前者 启动时检测重复 intent 并报错
无用代码 AgentSkillDispatcher.dispatch() 无调用方 可删除，或统一改为经它分发
