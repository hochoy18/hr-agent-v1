files.py 三大 exec 节点详解

resume_exec / interview_exec / exam_exec 是文件驱动流式接口在 LangGraph 图中的"直通执行节点"。本文沿 前端面板 → HTTP 端点 → 图路由 → 节点 → 服务层 的完整链路，讲清每个节点使用的功能、前端页面入口、目的与实现。

📦 app/agent/nodes/files.py 🧭 前端入口 · 调用链路 🕸 LangGraph + SSE 📅 2026-11

1全景概览

普通聊天走 /agent/graph/chat，由路由节点做意图识别；但上传文件类的重操作（批量评分、生成面试计划、生成试卷）有专用 HTTP 端点 app/api/v1/endpoints/agent.py， 前端已经明确知道要干什么，不需要再让 LLM 决策一次。于是图里为它们准备了三个"直通执行节点"：

💡 一句话区分 resume_exec 按 JD 批量评分简历（招聘链路起点）； interview_exec 为某位已评分候选人生成面试方案（中间环节）； exam_exec 按确认的配置 + 参考文档/面试方案出笔试试卷（链路末端）。 三者串起来就是产品主线：JD → 筛简历 → 面试计划 → 笔试试卷。

2共同机制：为什么会有这三个节点

files.py 文件头注释写明了设计意图：专用端点解析 FormData 后，以 preset_intent 直接把图路由到对应 exec 节点；节点内部复用既有流式生成器，事件经 stream writer 透传给 bridge.run_stream()。

2.1 preset_intent 直通路由 跳过 LLM 决策

端点调用 run_stream(preset_intent="resume_exec"/"interview_exec"/"exam_exec") endpoints/agent.py:122-127,147-152,176-181,213-217。 路由节点检测到 preset 非空时，不做意图识别、不构建对话记忆，直接把目标节点写进 state： 

# app/agent/nodes/routing.py:24-34
preset = state.get("preset_intent")
if preset:
    logger.info("LangGraph 路由直通 preset=%s", preset)
    return {
        "intent": preset,
        "agent_plan": {"mode": "tool", "intent": preset,
                      "reason": "端点直通执行。", "source": "preset"},
        "route": None,
        "memory_context": "",
        "dest_node": preset,   # 条件边据此直达 exec 节点
    }

2.2 文件与定位参数走 configurable，不进 checkpoint 避免大 payload 落库

几十份简历的二进制内容如果进图状态，会被 checkpointer 序列化落库。所以端点把文件和参数放进 extra_config，最终挂在 RunnableConfig["configurable"] 上，节点内用两个小工具取出： 

# app/agent/nodes/files.py:22-27
def _exec_params(config: RunnableConfig) -> Dict[str, Any]:
    return (config.get("configurable") or {}).get("preset_params") or {}

def _exec_files(config: RunnableConfig):
    return (config.get("configurable") or {}).get("files") or []
configurable 键内容谁在用
files[{filename, content(bytes)}]，端点 _read_files() 读出的上传文件resume_exec、exam_exec（带文档时）
preset_params定位/配置参数：job_description_id / resume_evaluation_id / exam_requirements三个节点各取所需
user_id / agent_service当前用户 id 与注入了 DB session 的服务实例所有节点（_service(config)）

2.3 复用旧流式生成器：透传 + 终态回写 节点不做业务

三个节点结构完全一致：取 service → 取参数 → 跑生成器 → 返回终态。业务全部在 AgentService.stream_xxx() 里，节点只是包一层： 

# app/agent/nodes/legacy.py:66-76 —— 迭代生成器，事件分流
async def _emit_generator(agen) -> Optional[Dict[str, Any]]:
    writer = get_stream_writer()
    final_event = None
    async for event in agen:
        if event.get("type") == "final":
            final_event = event        # final 不透传，留作 state 更新
            continue
        if writer:
            writer({"agent_event": event})  # progress/delta/artifact → SSE
    return final_event

# legacy.py:54-63 —— final 事件转 state 更新（写入 checkpoint）
def _respond_from_event(final_event):
    dumped = (final_event or {}).get("response") or {}
    return {"final_response": dumped, "intent": dumped.get("intent"),
            "route": dumped.get("route"), "steps": ..., "artifacts": ...}
✅ SSE 事件契约（三节点通用） progress 步骤条进度 → delta markdown 增量文本 → artifact 阶段性产物 → final 终态响应（message / intent / route / steps / artifacts / suggestions）。 端点 _sse_stream() 统一包装为 data: {...} 帧，异常转 error 事件，结尾固定 [DONE] endpoints/agent.py:40-59。

# app/agent/nodes/files.py:30-40
async def resume_exec_node(state, config):
    service = _service(config)
    params  = _exec_params(config)
    files   = _exec_files(config)
    final_event = await _emit_generator(service.stream_resume_screening(
        user_id=config["configurable"]["user_id"],
        job_description_id=UUID(str(params["job_description_id"])),
        files=files,
        conversation_id=state.get("conversation_id"),
    ))
    return _respond_from_event(final_event)
