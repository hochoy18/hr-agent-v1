chat / agent / agent-graph 三组 API 详解

同样挂着"对话"的名字，三组端点背后是完全不同的执行模型。本文对照后端实现与前端调用点，说清它们各自解决什么问题、从哪个页面进入、什么时候该用哪一个。

📦 backend / app / api 🧭 端点定位 · 前端落点 🕸 LangGraph + SSE 📅 2026-11

1全景概览

三组路由都注册在 api_router 上 app/api/v1/api.py:16,27,28， 最终统一挂在 /api/v1 前缀下。它们不是同一能力的三个版本，而是三种不同的交互模型：

/api/v1/chat/*ChatService · 单层 LLM 调用
前端调用 0 处
无页面入口后端保留的通用聊天能力
/api/v1/agent/graph/*LangGraph · 意图路由 + interrupt
HRAgent 输入框 / 确认按钮侧边栏「HR Agent」→ /agent
/api/v1/agent/*LangGraph · preset_intent 直通
HRAgent 消息内工具面板上传简历 / 面试计划 / 试卷生成
图 1 · 三组端点与前端落点：只有后两组被前端实际使用
💡 一句话区分 /chat 是"问什么答什么"的通用聊天，不进图、没有工具； /agent/graph 是 Agent 的主对话入口，负责判断意图、执行任务、暂停等用户确认； /agent 是"用户已经点明要做什么"时的直通执行通道，跳过意图识别，直接跑对应业务节点。
⚠️ 先澄清一个书写问题 提问中出现的 prefix="@command:chat" 是 IDE 斜杠命令补全菜单留下的残留文字，源码里实际是 prefix="/chat"。三组前缀分别是 /chat、/agent、/agent/graph。

2三组端点定义

2.1 路由注册

# app/api/v1/api.py:16,27,28
api_router.include_router(chat.router,        prefix="/chat",       tags=["chat"])
api_router.include_router(agent.router,       prefix="/agent",      tags=["agent"])
api_router.include_router(agent_graph.router, prefix="/agent/graph", tags=["agent-graph"])

三个文件头部的注释其实已经写明了定位： chat.py 自述"通用聊天，不负责复杂 HR Agent 工具编排" endpoints/chat.py:1-9； agent.py 自述"文件驱动的流式接口，全部经 LangGraph 图执行（preset_intent 直通对应 exec 节点）" endpoints/agent.py:1-14； agent_graph.py 自述"Agent 模块迁移 LangGraph 后的新入口" endpoints/agent_graph.py:1-19。

2.2 一表看懂差异

维度 /chat/* /agent/* /agent/graph/*
定位 通用大模型聊天 场景直通执行：调用方已知要做什么 Agent 主对话：自然语言 → 意图路由
底层实现 ChatService → LLMService 直接调模型 仍走 LangGraph，但 preset_intent 跳过 route_intent 完整 LangGraph：路由 → 子图/exec → interrupt
是否做意图识别 否 跳过（由端点固定） 是（ReAct / 规则 / 确认直通）
入参形态 JSON：message + conversation_id + context multipart 文件 / 固定资源 ID / confirmed_requirements JSON：message + thread_id + attachments + confirmed_requirements
响应协议 /send 返回 JSON；/stream 为 text/plain 的 {"token":...} 帧 标准 SSE：progress / delta / artifact / interrupt / final + [DONE] 同左（两者共用同一套事件契约）
中断确认 无 无（确认数据已在入参里） 有：interrupt → /resume
会话持久化 后端自己写 messages 表 前端调用 /conversations 落库 前端落库；图状态由 checkpointer 保存
前端调用方 0 处 HRAgent 页内工具面板 HRAgent 页内聊天框 + 确认按钮
✅ 关键认知 /agent 和 /agent/graph 不是两套 Agent 实现，它们最终进入同一张 LangGraph 图、共用同一套 SSE 事件格式。唯一区别是：/agent 通过 preset_intent 跳过"猜意图"这一步。

3/chat：通用对话

提供四个端点，覆盖最基础的聊天闭环：

方法路径作用
POST/chat/send一次性返回完整 AI 回复（ChatResponse）
POST/chat/stream逐 token 流式返回
GET/chat/suggestions根据输入生成建议问题
POST/chat/feedback给消息提交评分与反馈

3.1 后端链路 单层 LLM · 无编排

核心逻辑在 ChatService.process_message() app/services/chat_service.py:95 与 stream_message() app/services/chat_service.py:173，流程非常直白：

POST /chat/send 或 /chat/stream
get_or_create_conversation()校验会话归属，无则新建
保存用户消息 + 取最近 20 条历史conversation_service.add_message / get_conversation_messages
仅当传入 context 时
DocumentService.search_documents()当前是 ilike 子串匹配，pgvector 占位实现
LLMService.generate_response / stream_response拼历史 + 检索片段，直接生成
保存助手消息 → 返回 / 流式输出
图 2 · /chat 的执行链路：没有工具、没有意图、没有确认
⚠️ 文档检索比看起来弱 代码条件是 if context and context.get("search_documents", True)——不传 context 时根本不会检索。即使触发，检索实现也只是 Document.extracted_content.ilike("%query%") app/services/document_service.py:242-246， 用整句用户问题做子串匹配，命中率通常很低。

3.2 响应格式

两个写接口的返回结构并不统一，接入时要注意：

端点Content-Type数据形态
/chat/send application/json ChatResponse：message_id / conversation_id / content / role / timestamp
/chat/stream text/plain（不是 text/event-stream） 逐行 data: {"token": "...", "type": "token"}，最后 data: {"type": "complete", ...}

虽然 /chat/stream 也加了 data: 前缀，但它没有 event: 字段、没有 [DONE]、也没有 progress / artifact / interrupt 等事件类型，不能和 Agent 的 SSE 解析器复用。

3.3 前端现状 零调用

在 frontend/src 与 frontend/dist 中检索 /api/v1/chat、chat/send、chat/stream，均无任何命中。 也就是说这组端点在当前前端没有任何页面入口、没有任何使用场景，是一组"后端注册了、前端没接"的通用能力。

它仍出现在 API 文档的"通用对话"章节 docs/origin/md/2-MD-企业级项目文档/06-API接口清单.md:1589， 属于面向第三方接入或后续功能的预留接口。

🚫 不要把它和「知识问答」页面搞混 侧边栏「知识助理 → 知识问答」（/assistant/qa）调用的不是 /chat/*，而是 RAG 工作流 POST /knowledge-assistant/ask frontend/src/views/assistant/KnowledgeAssistant.vue:532。 前者是"选知识库 + 带引用来源"的检索增强问答，后者是裸 LLM 聊天。

4/agent：场景直通

这组端点的共同点：调用方已经知道要执行哪条业务链（因为用户点了按钮、选了文件、填了表单），所以不需要再让模型判断意图。 它们仍然进入 LangGraph，只是用一个固定值把路由节点"短路"掉。

4.1 preset_intent 机制

AgentGraphService.run_stream() 接收 preset_intent app/agent/bridge.py:109-160， 把它写入图状态；route_intent_node 开头直接检查该字段 app/agent/nodes/routing.py:16-25， 命中则跳过后续的规则快筛 / ReAct 决策，直接返回对应目标节点。

POST /agent/resume-screen/stream 等
run_stream(preset_intent="resume_exec")files / preset_params 走 extra_config，不进 checkpoint
route_intent_node：preset 是否为空？
非空 → 直通
resume_exec 执行节点跳过 ReAct 观察与意图分类
SSE 输出（与 /agent/graph 同契约）
图 3 · preset_intent 不是绕过图，而是跳过"猜意图"这一步
ℹ️ 为什么文件不放图状态里 上传文件等大 payload 通过 extra_config 合并进 configurable app/agent/bridge.py:152-160， 不写入 checkpoint，避免 LangGraph 持久化巨大的二进制内容。

4.2 端点清单

端点preset_intent入参场景 / 前端触发
/agent/stream jd JSON，必须带 confirmed_requirements JD 确认后执行生成链；仅在前端 thread 丢失时作为降级通道
/agent/resume-screen/stream resume_exec multipart：job_description_id + 最多 20 份简历 HRAgent 消息内"简历评分"面板，上传简历后点击开始评分
/agent/interview-plan/stream interview_exec multipart：resume_evaluation_id HRAgent 消息内"面试计划"面板，选择已评分候选人
/agent/exam/stream exam_exec JSON，必须带 confirmed_requirements HRAgent 试卷面板，无参考文档时生成试卷
/agent/exam/document-stream exam_exec multipart：考试配置 JSON + 最多 5 个参考文档 HRAgent 试卷面板，基于上传文档生成试卷

所有端点都经过 _sse_stream() 统一包装 endpoints/agent.py:40-59： 自动补 thread_id、捕获异常为 {"type":"error"}、最后输出 data: [DONE]。

5/agent/graph：主对话入口

只有两个端点，却是整个 Agent 能力的正门：

方法路径作用

5.2 resume：中断恢复 checkpointer 驱动

当 JD 信息不全或邮件待确认时，图会在 jd_confirm 等节点触发 interrupt，SSE 先推 interrupt 再推一个 requires_confirmation: true 的 final app/agent/bridge.py:193-210。 前端拿到 thread_id 后，把确认表单 POST 到 /resume，后端用 Command(resume=value) 从断点继续 endpoints/agent_graph.py:131-142。

5.3 SSE 事件契约

两组 Agent 端点共用同一个包装器（_sse_stream / _sse_wrapper），事件类型如下 endpoints/agent_graph.py:1-19：

7选型指南

需求推荐入口理由
用户在聊天框自由表达，需要多轮、确认、产物 /agent/graph/chat + /resume 唯一具备意图路由、interrupt 确认、checkpoint 续跑的入口
用户已点按钮，且手里有文件或资源 ID /agent/* 跳过意图识别，结果最确定，避免"赌"模型分类正确
基于知识库的文档问答，需要引用来源 /knowledge-assistant/ask RAG 专用链路，带知识库选择与来源返回
最朴素的通用聊天 / 第三方接入 /chat/* 够轻量，但无工具、无前端页面，检索能力很弱
固定表单驱动的确定性流程 /hr-workflows/* 不依赖模型决策，适合结构化输入与批处理
✅ 判断口诀 "要不要让模型决定做什么？" —— 要，走 /agent/graph/chat；不要，走 /agent/*；连业务工具都不需要，才轮到 /chat。
