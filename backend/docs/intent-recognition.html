HR Agent 意图识别机制详解

用户一句话进来，系统如何判断"要问知识库、生成 JD、筛简历，还是只是闲聊"？本文拆解项目中两套意图识别机制的完整链路与设计取舍。

📦 backend / app 🧭 意图分类 · 路由分发 🕸 LangGraph + ReAct 📅 2026-11

1全景概览

项目中有两套意图识别机制，服务于两个不同入口，共享同一套底层关键词规则，但复杂度与能力差异很大：

2.3 第一级：关键词快筛

classify_intent_fast() intent_service.py:45 对有序的 (意图, 关键词列表) 做大小写不敏感的子串匹配，命中即返回，全部未命中返回 None（"我不确定"的信号）。

def classify_intent_fast(self, query: str) -> Optional[str]:
    q = query.lower()
    for intent, words in self.keywords:   # 有序列表，顺序即优先级
        for w in words:
            if w.lower() in q:          # 子串包含匹配，无分词无正则
                return intent
    return None                          # 交给 LLM
✅ 两个刻意的设计细节 顺序即优先级：resume_screening 排最前、kb_qa 排最后——一句话同时含"简历"和"知识库"时优先判为简历筛选，兜底性质最强的放最后。
关键词粒度混合：既有完整短语（"简历筛选"），也有裸词（"JD"、"QA"），提高召回。

2.4 第二级：LLM 兜底分类（三层防御）

classify_intent_with_llm() intent_service.py:62 把 LLM 当作分类器而非对话模型使用：

防御一：约束式 Prompt列出 6 个标签及含义，要求"仅返回标签之一，不要解释"
LLM 可能不听话，返回 "意图是：jd" 或中文
防御二：输出容错清洗非法标签 → 中英文关键词二次模糊归一化
归一化也失败 / 调用抛异常
防御三：双重兜底一律返回 kb_qa —— 本方法永不失败
图 3 · LLM 分类的三层防御：任何情况下入口链路都有结果
  • 懒加载：self.llm_service 只在真正走到 LLM 分支时才实例化 intent_service.py:86——关键词能解决时连 LLM 客户端都不初始化。
  • 默认值选 kb_qa：问答是最通用、副作用最小的功能，异常时记日志后静默降级，入口永不 500。

2.5 kb_qa 的特殊增强：自动选知识库

get_route_for_intent() intent_service.py:135 中，若意图是 kb_qa，不只给页面地址，还调用 KBSelectionService.select_kb_for_question()（候选上限 200）自动挑一个最相关的知识库，把 kb_id 一并返回——前端跳到问答页时知识库已预选好。选择失败也不阻断，kb_id = None 交给前端处理。

3.2 ① preset 直通 跳过识别

文件流等专用端点已经知道用户要干什么，直接在 state 里塞 preset_intent nodes/routing.py:25，完全跳过意图识别与记忆构建，直达目标节点，source: "preset"。

3.3 ② 用户确认直通 多轮保障

多轮交互中，用户上一轮被追问、这一轮回传了 confirmed_requirements（表单确认），就不再重新分类 reasoning.py:58：

  • 确认的 action 匹配到 skill（如 send_email）→ 对应 skill intent；
  • 否则默认回 jd 工具链。
💡 为什么需要这一级 避免"确认消息被重新识别成别的意图"——用户点确认按钮回传的结构化数据不该再走一遍自然语言分类。

3.4 ③ 规则快通道 零 LLM 成本

build_rule_agent_plan() + classify_agent_intent() reasoning.py:96-177 是纯本地规则，但比入口一的关键词表强很多：

规则逻辑产出意图
正则组合 "删除/删掉/移除/清理" 且 提到 "jd/职位/简历/候选人/面试/试卷/考试" resource_delete
专用编辑识别 _is_jd_edit_request / _is_criteria_edit_request，区分"生成 JD"和"修改刚才的 JD" jd_edit / criteria_edit
复用关键词表 调用入口一的 intent_service.classify_intent_fast()——两套机制共享底层规则 6 个基础意图
附件上下文 上传了 PDF/Word/TXT 且 消息含"评分/筛选" → 筛简历；含"试卷/出题" → 生成试卷。同样的话，带不带附件意图不同 resume_screening / exam_generate
多轮 followup 识别"继续给这批候选人生成面试"这类承接上文的请求 interview_plan / exam_generate
删除候选继承 上一轮刚列出删除候选清单，用户只回了一个名字或"第二个" → 继续删除确认流程 resource_delete
⚠️ 顺序陷阱（代码注释中特意强调） "删除候选继承"规则必须放在通用意图规则之后 reasoning.py:166-169——否则"生成一个JD<候选名>"这类含候选名称的明确意图会被抢先路由进删除流程。

3.5 ④ ReAct 观察型路由 核心亮点

规则都没命中时，plan_agent_action() reasoning.py:197 → run_router_agent() app/agent/routing_agent.py:118。这不是简单让 LLM 输出标签，而是一个带工具的 ReAct Agent：

输入：消息 + 对话记忆 + 附件清单 + 线程产物数
Router LLM（专用路由模型 get_router_model）系统提示：动作空间 + 决策规则 + 合法 intent 集合
用户说"刚才 / 上次 / 这个 / 那个"等指代时
只读工具 search_resources观察当前用户 / 当前对话最近的资源（循环，受 recursion_limit 约束）
观察到了什么，再决策
RouterDecision（Pydantic 强约束结构化输出）mode + action + intent + thought + confidence + reply
图 6 · 观察型 ReAct 路由：先观察、再决策，解决指代消解问题

结构化决策 RouterDecision routing_agent.py:29 的字段约束：

字段约束说明
actionchat use_tool ask_user 三选一闲聊 / 执行任务 / 缺前置条件追问
modechat / toolvalidator 强制与 action 一致
intent必须 ∈ tool_registry 意图集 + general系统提示中枚举，越界即回退规则
thought / confidence一句推理摘要 / 0-1 置信度可观测、可审计
reply仅 action=chat 时非空闲聊直接给自然回复
🔒 安全边界
  • 路由器只"选路"，不持有写工具——删除、发送、落库全部由后续确定性子图执行
  • 系统提示明确："邮件只能生成草稿，不允许自动发送"
  • "不确定时优先 chat，避免误触发工具"
  • "删除类请求只有工具观察到明确目标时才选 resource_delete，不要臆造名称或 ID"
🛠 工程保障
  • agent 按 (意图集, 工具说明) 缓存复用，skills 变化自然换 key
  • asyncio.wait_for 超时控制 + 最多 N 次重试拿结构化输出
  • intent 非法 / 调用失败 → 回退本地规则，链路永不中断
  • AGENT_ROUTER_MODE=rule/react 可配置切换，非法值按 rule 处理
✅ 为什么比"LLM 直接分类"强 用户说"删掉刚才那个 JD"时，模型可以先调工具查当前对话最近的资源，观察到了什么再决策——指代消解是纯关键词和单次分类 LLM 都做不到的。同时受限动作空间（chat / use_tool / ask_user）让 LLM 的输出可被程序安全消费。

5设计哲学与改进建议

共同的设计哲学

💰 成本分层

确定性的便宜规则优先，LLM 只处理长尾。大部分明确请求（"帮我生成JD"）根本不用调大模型，省钱省时。

🧱 结构化约束

LLM 输出用 Prompt 约束 + Pydantic 校验收窄到合法集合，非法输出有归一化和回退，保证可被程序安全消费。

🪂 层层降级

每一层失败都有默认路径：LLM 挂了回规则，规则不中回闲聊/问答。入口永不 500，链路永不中断。

🔀 路由与执行分离

路由器只选路不执行写操作；删除、发送、落库由确定性子图完成，LLM 的不确定性被隔离在决策层。

潜在问题与改进方向

问题说明改进建议
关键词误伤 裸词子串匹配无法处理否定语义："不用生成试卷，我只想问问知识库"会命中"试卷"被路由到出题页 对含否定词的 query 跳过 fast 层直接走 LLM/ReAct
归一化顺序隐患 入口一 LLM 输出清洗中 if "jd" in intent 排第一，若返回一段含多词的解释文本会被第一个规则截胡 先做精确匹配，再按标签特异性排序模糊匹配
无缓存 相同 query 每次都重新分类（LLM 分支） 高频场景加 LRU 缓存
硬编码参数 知识库选择 max_candidates=200 写死，库多时开销值得关注 移入 settings 配置
入口一无闲聊类别 文件头注释提到"还是聊天"，但 6 个标签里没有 chat，闲聊被强行归入 kb_qa（入口二已有 general/chat） 如需统一，可为入口一补充 chat 标签
