00模块地图

系统有五个业务域，共用一套用户、权限、文件与对话基础设施。每个域都遵循同一个模式：AI 生成初稿 → 落结构化表 → 人可编辑可复核。

业务域核心能力AI 参与方式

Agent意图路由、工具调度、确认规则 + ReAct 路由；写操作交确定性节点

01招聘主链路

五个环节，五次「AI 产出 + 人确认」。链路的每一环都把结果落成表，下一环通过外键读取上一环的产物，而不是把上下文塞回提示词里。

1.1 各环节实现要点

环节调用关键实现
需求解析本地规则 + LLM 解析出岗位名称、地点、薪资、经验、学历、技能；缺字段时走确认弹窗补全，而不是直接失败。确认 payload 里带 missing_fields。
JD 生成Dify type=1 流式返回片段；生成后同时产出配套评分标准。保存时 title 与 content 必填，默认状态为草稿。
评分标准Dify type=2 输出维度、权重、满分与说明；total_score 默认 100。维度之和与总分口径需人工确认。
简历筛选Dify type=3 PDF/DOC/DOCX 提取文本（pdfplumber / pdfminer.six / python-docx / docx2txt），结合 JD 与评分标准输出总分、维度分、理由；结果写 model_score_detail。
面试方案Dify type=4 必须关联一条已完成的简历评估；输出面试目标、流程、核心问题、追问建议、考察维度、评分建议、风险点。

1.2 解析失败怎么处理

简历解析是这个链路最脆的一环——扫描件、双栏排版、表格、乱码都会让提取结果错位。处理原则只有一条：解析失败不生成虚假评分。

文件层

校验格式与大小（默认 10MB）。格式不支持直接拒绝，不进入解析队列。

解析层

提取为空或明显残缺时标记失败，返回可理解的失败原因，允许重新上传。

评分层

文本不可用时不做「兜底打分」。宁可让用户重传，也不给一个没有依据的分数。

一个容易被忽略的约束

简历评估必须关联 JD。这不是数据完整性要求，而是业务要求：没有 JD 就没有评分基准，模型会按「通用优秀简历」打分，结果与岗位完全无关。评分标准可选，但选了就必须与 JD 口径一致。

02面试 AI 评价链路

这是整个项目最复杂的模块，也是最值得看的部分。它要解决的问题是：把一段几十分钟的多人对话，变成一份有证据、可复核、可复算的评价报告。

2.1 四段流水线

2.2 转写结构化：先承认它不完美

转写稿来源多样：腾讯会议导出的 docx、第三方 ASR、人工逐字稿。格式差异很大，所以解析器用多组正则覆盖常见形态：

格式示例
名字 + 括号时间戳伍双林(00:00:07): 我们先聊聊项目
名字 + 日期时间Jeff 2026-11-09 21:01:42（腾讯会议 docx 导出，头行独占）
名字 + 纯时间说话人1 00:00:07

名字校验会排除「句子、日期、纯数字」这类误命中：长度不超过 20，且不能包含标点、空格、括号。这看着琐碎，但不做就会出现「把正文里的（10:30）当成说话人」这种问题。

候选人身份不做推测

resolve_candidate_speaker 只按人工填写的姓名去对标签，对不上就返回 None，由调用方决定是否让模型在既有标签里指认。这条约束很重要：身份判断错了，整份评价的问答方向会完全颠倒——把面试官的话当成候选人的回答来打分。

2.3 问答配对：一条规则解决大部分情况

backend/app/services/qa_pairing.py
def pair_qa_turns(dialogue):
    candidate = dialogue.candidate_speaker
    if not candidate:
        return PairingResult()          # 身份不明，无法配对

    result, pending = PairingResult(), []
    for turn in dialogue.turns:
        if turn.speaker != candidate:
            pending.append(turn)          # 面试官轮攒成提问块
            continue
        if not pending:
            result.unprompted.append(turn)  # 候选人先开口 → 开场自述
            continue
        result.pairs.append(_build(len(result.pairs) + 1, pending, turn, candidate))
        pending = []
    if pending:                          # 结尾有问无答 → 未作答信号
        result.pairs.append(_build(len(result.pairs) + 1, pending, None, candidate))
    return result

不做插话/打断的特殊处理，也不合并跨轮的回答。原因：真实面试里插话形态太多，规则越细误判越多；把边界交给后续 LLM 判定更稳，因为它的输入已经是「一问一答」的清晰结构。

四项自查（不调模型）

内容守恒

结构化后的文本不能丢原文内容，拼接回去应与原文一致。

段号连续

S1..Sn 不能跳号，否则说明解析时漏段。

相邻轮说话人不同

同一人连续发言应已合并；若相邻轮同名，说明合并逻辑失效。

原文行号可定位

每轮都能回指原文位置，证据才可核对。

自查命令
# 只跑结构与配对，不调模型
python scripts/inspect_transcript.py <转写文件> --candidate 姓名

# 连模型实收的提示词一起看（改提示词前先确认规则真的渲染进去了）
python scripts/inspect_transcript.py <转写文件> --candidate 姓名 --prompt

# 从库里取某场面试的转写（支持 UUID 前缀）
python scripts/inspect_transcript.py --interview-id <id>

2.4 逐组判定：三个字段，十二个档位

判定阶段模型只做一件事：给每组问答打三个标签。它不配对、不打分、不算总分。

字段问题档位
verdict
问题回应质量		 这段回答有没有回应面试官问的那件事？ 未作答 回避 答非所问 部分切题 切题
precedence 10 / 20 / 25 / 30 / 40，先判先得
substance
事实层级		 抛开答得好不好，能提取到哪一层事实？ none=0（只有态度）· claim=1（有名词无做法）· action=2（有做法无数据）· data=4（有数字/结果）
followup
追问深度		 面试官有没有就同一件事继续往下压？ none=0 · surface=2（追一层）· deep=4（连续两层以上）
唯一允许跨组看的字段，lookahead=2
每个档位都带反例

规则文件里每档不只有 criteria，还有 requires（何时命中）、excludes（什么情况不算）、examples{hit, miss, ambiguous}（含反例）。例如「未作答」的 excludes 明确写了「候选人承认不会，但同时给了替代经历——归部分切题或切题」。

反例比正例更能稳定判定。只给正例时，模型容易把「短但有内容」的回答判成未作答。

2.5 算分：能数出来的交给代码

四个维度的算法不一样，这是有意设计的：

维度计分方式权重说明
问答一致性verdict 分布 → 正面率 → 落档35%切题 1.0 / 部分切题 0.5 / 其他 0；≥0.9→4 档，≥0.7→3，≥0.4→2，≥0.1→1，否则 0
事实信息量substance 均值 → 四舍五入落档35%none 0 / claim 1 / action 2 / data 4；未作答组不计入均值
逻辑条理性模型按 rubric 判档15%只有文字 rubric，未纳入规则文件
表达组织能力模型按 rubric 判档15%同上
总分 = Σ(权重 × 分数 / 满分) / Σ权重 × 100。只计可评分维度；缺失维度的权重按比例归一到其余维度——少一维不会压低总分。

2.6 规则文件是唯一来源

app/rules/interview_rules_v1.json（当前 rule_version = v1.1）同时充当提示词生成源和算分参数来源。改口径只改这一个文件，并升版本号。

为什么有两维没进规则文件

逻辑条理性、表达组织能力合计占 30%，但只有文字 rubric（「基本完整」「偶有重复」这类程度词），没有可复核指标。项目实测过：填充词密度、平均句长、结构词密度与内容质量无正相关（结构词密度为 −0.36）。写进文件只是把主观判断换个格式存放，不会让它变得可核对。

文件里的 unscored 记录了纳入条件：先用影子模式跑 20–30 份真实稿，与人工基准相关性达 0.6 以上再纳入。

2.7 强制「待定」的四种情况

条件原因
可评分维度 < 3样本太少，总分没有代表性
转写 < 800 字内容不足以判断，硬打分等于编造
问答全部失败配对或判定环节出问题，分数不可信
判定缺标签 ≥ 20%模型输出不完整，统计口径已被破坏

命中任意一条，结论强制「待定」并在 notes 说明原因。这是「宁可说不知道」的具体实现——比给一个看似精确的 62 分更负责。

2.8 人工修订的三条约束

01只改分数，不改标签

verdict / substance 始终是模型的。修订的语义是「不同意这个档」，不是「重判问答组」。否则证据链就断了。

02AI 原分只在首次定格

之后再改仍以模型那版为基准，避免基准自身漂移。否则改三次之后，已经说不清「AI 原来给多少」。

03素材不足可转可评

insufficient 的维度一旦人工给分即转为可评分，并计入总分。人可以为自己的判断负责。

留痕写在 evaluation.manual_override：修订次数、AI 原总分、history[]（时间 / 操作人 / 原因 / 每维改前改后 / 结论变更 / 修订前后总分），保留最近 20 条。修订原因必填。

2.9 漂移与自查

backend/scripts/score_drift.py
# 同一份稿重复评分，输出极差 / 标准差 / 逐组标签翻转
python scripts/score_drift.py <转写文件> --candidate 姓名 --runs 10 --concurrency 3

它回答的问题是「同一份稿重复评分会不会给出不同结果」。当前已知的漂移来源写在规则文件的 known_gaps 里，两条都是实测出来的：

已知缺口实测现象拟改方向
均值把信息量压低 26 组样本：8 组 action、2 组 data、11 组 claim，均值 1.35 四舍五入到 1 档。有具体做法的回答占三分之一，分数体现不出来 改为按档位占比定档（如 data 占比 ≥20% 给 3 档），需先在多份真实稿上验证
正面率阈值贴着实测分布 切题率在 0.88–0.93 之间摆动，正好夹着 0.9 这条线；1 组问答翻转就让一致性从 4 档跳 3 档，总分随之跳 8.75 阈值按组数留余量（如「未正面回应 ≤1 组」才给 4 档）
这种「把缺陷写进配置」的做法值得学

known_gaps 不是待办清单，而是对使用者的免责说明：任何看到分数的人都能知道这个指标在什么情况下会失真。比起把问题藏在代码注释里，写在规则文件里更可能被读到。

04Skill 插件系统

Skill 的价值是不改核心代码就能扩展 Agent 能力。每个 Skill 是一个独立目录，声明 intent、阶段和执行脚本，由 dispatcher 按意图与阶段分发。

backend/skills/<skill-name>/ ├── SKILL.md Skill 描述（YAML frontmatter） ├── skill.json 清单：intent / phases / 脚本映射 ├── config.txt Skill 独立配置 └── scripts/ 各阶段执行脚本（如 draft.py / send.py）
backend/skills/hr-agent-email/skill.json
{
  "name": "hr-agent-email",
  "intent": "email_notification",
  "route": "/system/email-configs",
  "phases": ["draft", "send"],
  "default_phase": "draft",
  "confirmation_action": "send_email",
  "phase_scripts": {
    "draft": "scripts/email_draft.py:generate_email_draft",
    "send":  "scripts/email_send.py:send_confirmed_email"
  }
}
为什么 Skill 不做 interrupt

邮件确认的交互形态是「卡片 + 重新提交」，前端已经把确认内容作为一条新消息发出。改成 interrupt 需要同时改 UI、消息落库和草稿恢复逻辑，收益不足以支撑。这不是技术债，是按交互形态选择机制。

05评测体系

三套 runner 各管一段，共用「固定用例 + 结构化断言 + 基线对比」的方法。

runner覆盖校验维度

5.1 两层评分

规则评分器

确定性断言：字段是否存在、枚举值是否正确、step 状态是否合理。这部分不依赖模型，结果稳定可比。

可选 LLM judge

对开放式输出（如 JD 质量、回答相关性）做语义评分。average_judge_score 为空表示未启用，不参与判定。

5.2 回归怎么用

CI 里的用法
# 跑固定评估集，输出 JSON + Markdown 报告到 evals/reports/
python scripts/run_agent_evals.py --repeat-runs 3

# 与历史报告对比：指标回退或出现失败样例时非零退出
python scripts/run_agent_evals.py \
  --baseline evals/reports/agent_eval_latest.json \
  --fail-on-regression --fail-on-failed-cases
评测的真实成本

单次 16 个用例、平均延迟 4.5 秒，跑一轮约 1 分多钟；--repeat-runs 3 就是三倍。它不适合放在每次提交的钩子里，适合放在合并前或夜间任务。日常提交用 pytest，行为改动才跑评测。

06数据模型

实体关系本身不复杂，值得说的是两处设计：评价报告存在 JSON 字段里，图状态不进业务 ER。

6.1 evaluation JSON 里有什么

字段内容
dimensions[]四个维度的分数、档位、理由、证据
qa_pairs[]问答组、判定标签、统计
execution面试执行度（追问深度），不计入候选人分数
risk_signals[]风险信号
summary / strengths / risks总结、亮点、风险
recommendation / confidence推荐结论与置信度
insufficient / notes素材不足标记与原因说明
prompt_version / rule_version本次按哪版提示词与规则计算
manual_override修订次数、AI 原总分、history[]

6.2 为什么图状态不进 ER

AsyncPostgresSaver 启动时自动建四张表（checkpoints / checkpoint_blobs / checkpoint_writes / checkpoint_migrations），按 thread_id = conversation_id 存图的运行状态。

两套数据，互不替代

会话历史在 messages 表——那是「说过什么」。图状态在 checkpoints 表——那是「图跑到哪一步、攒了哪些产物」。把两者合并是常见的错误设计：会话历史要长期保留供检索，图状态只需要保留到该线程结束。

07工程实践与踩坑

问题现象处理
转写格式五花八门 腾讯会议 docx 导出、第三方 ASR、人工稿的时间戳写法都不一样；正文里的「（10:30）」被误识别为说话人 多组正则 + 名字合法性校验（长度、标点、纯数字排除）；四种格式各有对应规则

同一份稿评分不稳定 temperature=0 也不保证确定；分数极差可达数分 固定 seed=42；提供 score_drift.py 量化；已知缺口写进 known_gaps

7.1 三个值得复用的做法

01能数出来的交给代码

配对、切分、统计、算分都用确定性代码。模型只做「需要语义理解」的判断，且输出限定在枚举标签内。这样即使模型换版本，分数口径也不变。

02口径与提示词同源

同一份 JSON 既生成提示词，又编译成算分常量。模型看到的阈值与代码用的阈值必然一致，不会出现「reason 说不错但分很低」。

03把缺陷写进配置

known_gaps 记录已知失真场景与实测数据。使用者知道边界在哪，比给一个看起来精确的数字更可信。
