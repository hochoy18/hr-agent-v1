01选型方法论

这个项目的选型不是「哪个技术先进选哪个」，而是按五个维度打分。权重不同：可维护性 > 场景匹配 > 运维成本 > 生态成熟 > 性能上限。原因很实际——这是一个由小团队长期维护的内部系统，不是高并发 C 端产品。

35%可维护性

团队是否熟悉；出问题能否定位；新人接手成本。这一项否决过两个候选方案。

25%场景匹配

是否原生支持「状态 + 中断 + 流式」这类本项目刚需，而不是靠 hack 拼出来。

20%运维成本

多一个组件就多一套备份、监控、升级、故障排查。能用现成数据库解决就不新引入。

12%生态成熟

文档、社区、版本稳定性。避免踩在快速变化的项目上。

8%性能上限

当前量级（内部试点、日请求千级）远未触顶，性能只在「会不会成为瓶颈」层面评估。

否决项

需要专职运维的新中间件；锁定在单一厂商且无迁移路径的 SDK；文档缺失的小众框架。

一个反直觉的结论

这个项目里最难的不是选技术，是选边界。比如「Dify 还是自研」不是二选一：把长文本生成放 Dify（业务能自己改提示词），把编排、确认、落库留自研（需要事务与回滚）。混着用比统一用更难解释，但它是唯一同时满足「迭代快」和「不出事」的方案。

2.3 前端分层与数据流

前端有一条自我约束：不把业务状态存在前端。store 里只有登录态，其余一切以接口返回为准。原因是 Agent 会话有服务端 checkpoint，前端若再存一份，两边不一致时无法判断谁对。

2.4 SSE 的消费方式

浏览器原生 EventSource 不支持自定义请求头，无法带 Authorization。项目改用 fetch + ReadableStream 手动解析：

frontend/src/api/agent.js（示意）
// POST + 自定义头 + 逐行解析 data: 前缀
const res = await fetch(url, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
  body: JSON.stringify(payload)
});
const reader = res.body.getReader();
const decoder = new TextDecoder();
let buf = '';
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buf += decoder.decode(value, { stream: true });
  const lines = buf.split('\n');
  buf = lines.pop();                       // 保留不完整的最后一行
  for (const line of lines) {
    if (!line.startsWith('data: ')) continue;
    const evt = JSON.parse(line.slice(6));  // 按 type 分发到 UI
  }
}
按 \n 切分时必须保留最后一段，否则跨 chunk 的事件会被截断——这是 SSE 前端实现最常见的坑。

03后端框架

3.1 FastAPI vs Django vs Flask

维度FastAPIDjangoFlask
异步支持原生 async def 全链路有限 3.x 起支持但生态仍偏同步需扩展
SSE / 流式简单 StreamingResponse 直接吐需借助 StreamingHttpResponse可行但不自然
参数校验Pydantic 内建，OpenAPI 自动生成Form / DRF Serializer需自行集成
鉴权依赖Depends 组合，天然适合 RBAC中间件 + 装饰器装饰器
管理后台无内建强 Admin 开箱即用无
本项目结论本项目有长时 LLM 调用、SSE 流、文件上传三类异步场景，FastAPI 的 async 与 Pydantic 校验直接命中；管理后台可用前端自建，不需要 Django Admin。

3.2 数据访问：SQLAlchemy 2.0 Async + asyncpg

选了什么

业务链路统一 AsyncSession + asyncpg 驱动；模型用 2.0 声明式风格；迁移用 Alembic。查询在 service 层完成，endpoint 只做参数绑定与响应封装。

为什么不用同步 ORM

LLM 调用动辄 3–20 秒，同步驱动会占住线程。全异步后单进程可承载更多并发请求，且与 FastAPI 事件循环一致，不会出现「async 路由里跑同步 DB」的隐性阻塞。

两套连接池共存，必须核算

业务侧用 asyncpg 池（DATABASE_POOL_SIZE 默认 10），LangGraph checkpointer 用独立的 psycopg_pool.AsyncConnectionPool（同样读这个配置）。两者各自独立，合计不能超过 PostgreSQL 的 max_connections。多实例部署时按「实例数 × 两池之和」核算，这是最容易在上线后踩到的坑。

4.3 依赖版本锁定

LangChain 生态版本耦合极强，langgraph 与 langchain-core 的小版本错配就会在运行时报属性错误。项目采取精确锁定（==）而非范围约束：

包锁定版本作用
langgraph1.0.10状态图、条件边、interrupt、astream
langgraph-checkpoint3.0.1checkpoint 协议
langgraph-checkpoint-postgres3.0.1AsyncPostgresSaver
langgraph-prebuilt1.0.8预置图与 agent 构造
langchain1.0.8create_agent / ToolStrategy
langchain-core1.1.0消息、Runnable、stream writer
langchain-openai1.0.3ChatOpenAI，接 DashScope 兼容端点
langchain-postgres0.0.16PGVector 向量存储
升级策略

这类依赖不做「顺手升级」。升级必须同时通过三关：pytest 全绿 → Agent 评测集无回退 → 手工验证 interrupt/resume 一次完整确认流。历史上 interrupt 的恢复语义在 1.0 的小版本间有过行为变化，只跑单测发现不了。

4.4 框架内混用两种 Agent 构造

路由侧：create_agent + ToolStrategy

用 structured_output.ToolStrategy(RouterDecision) 强制模型产出结构化决策对象。失败时 structured_response 为空，由外层按次数重试，仍失败回退关键词规则。

对话侧：create_agent + 只读工具

挂 4 个只读查询工具，允许模型多轮 Thought → Action → Observation 后作答。工具只读，写操作在别的节点，这是安全边界而非能力限制。

backend/app/agent/routing_agent.py
agent = create_agent(
    model=get_router_model(),              # temperature=0，独立超时/步数/token 上限
    tools=ROUTER_TOOLS,                    # 只有 search_resources 一个只读工具
    system_prompt=_system_prompt(allowed_intents, tool_text),
    response_format=ToolStrategy(RouterDecision),
    name="hr_router_agent",
)

注意 get_router_model() 设置了 max_retries=0：路由失败要快速回退，而不是在 SDK 内部重试三次把主链路拖住。

05数据层选型

5.1 为什么用 pgvector 而不是专用向量库

维度PostgreSQL + pgvectorMilvus / QdrantChroma
部署形态复用现有 PG 实例，装扩展即可独立集群，需专职运维嵌入式，单机方便
事务一致性强 文档与向量同事务写入/删除弱 需应用层补偿单机事务有限
元数据过滤SQL 任意 JOIN，按知识库/用户/时间过滤支持标量过滤，但表达力弱于 SQL基础过滤
混合检索原生 向量 + tsvector 全文一次查询需两套索引分别查再合并需自行实现
规模上限百万级向量可用（HNSW / IVFFlat）十亿级十万级
本项目结论企业知识库规模在十万级以内，且「按知识库过滤」「删文档同步删向量」是高频操作，事务与 SQL 表达力比极限 QPS 更重要。

6.2 为什么对话与路由用两个模型配置

路由要「快且稳」

temperature=0 保证相同输入尽量相同决策；max_tokens=800 限制它絮絮叨叨；max_retries=0 让它失败就快速回退，而不是在 SDK 内部重试三次。路由慢一秒，用户感知的是整个系统慢。

对话要「自然」

temperature=0.7 让回复不那么僵硬；max_tokens 不设上限，避免长回答被截断。两者对延迟与风格的诉求不同，共用一个模型实例会互相迁就。

6.3 Dify 的定位

Dify 在本项目里不是「Agent 平台」，而是可热更新的提示词执行器。它承担四类长文本生成，因为这类需求的调整频率远高于代码：

类型能力为什么放 Dify
type=1JD 生成岗位话术与结构随行业/客户变化，业务侧自己调更快
type=2评分标准生成维度与权重口径需要 HR 负责人参与调整
type=3简历解析与评分提示词迭代频繁，且需与 JD 模板解耦
type=4面试方案生成题目风格随岗位线变化，不宜硬编码
什么不能放 Dify

任何需要事务、权限、跨表写入的动作都不能放：删除资源、发送邮件、保存评价、状态流转。这些必须在后端 service 里完成，Dify 只返回文本。

6.4 规则文件：提示词与算分同源

面试评价是这个项目里唯一把「评分口径」完全外置到配置文件的模块。interview_rules_v1.json 同时被三处消费：

消费方读什么
interview_service._apply_derived_scoresderivation 的 weights / bands / min_samples / exclude_group / rounding，算两维分数
interview_service.DIMENSION_WEIGHTSdimension_weights.weights，折算总分
interview_prompts 中的系统提示词derivation 渲染成档位表，模型看到的阈值与代码算分一致

好处很直接：模型看到的统计口径与代码算分的口径不会打架。坏处是改了常量需要重启（导入时编译 + lru_cache），这一点在运维手册里必须写明。

07通信与流式

7.1 为什么选 SSE

维度SSEWebSocket
通信方向服务端 → 客户端（够用）双向
协议普通 HTTP，复用鉴权头与网关需升级握手，部分网关需单独配置
断线处理浏览器自动重连语义简单需自行实现心跳与重连
服务端实现StreamingResponse 即可需连接管理器与广播
本项目结论生成任务本质是「一问、持续回吐」，没有双向需求，SSE 的简单性直接胜出。

7.2 事件契约

事件来源载荷与前端行为
progressastream(stream_mode="updates")节点名（子图带命名空间，如 jd_edit:locate）+ steps，驱动步骤条
delta节点内 get_stream_writer()文本增量，追加到气泡
artifact旧生成器事件透传结构化产物卡片（JD / 评分 / 方案 / 试卷）
interrupt捕获 __interrupt__thread_id + payload，渲染确认表单
final流结束后读 state.final_response完整响应，前端落库并结束本轮
error异常提示失败原因，保留输入可重试

08工程化与质量

8.1 三层测试体系

L1单元测试

pytest，覆盖 services / api / fixtures。锁的是契约与边界：规则文件取值、提示词渲染、算分函数、schema 校验。约 111 例（含参数化）。

L2Agent 评测集

固定用例 + 真实模型调用。校验 intent、route、requires_confirmation、missing_fields、steps（id/status）、artifacts（type）、响应签名稳定性。

L3基线回归

与历史报告对比，指标回退或出现失败样例时以非零码退出，可接 CI。这是唯一能发现「提示词改了导致路由退化」的手段。

回归命令
# 单测
./venv/bin/python -m pytest tests/ -q

# 评测：跑 3 轮，输出 JSON + Markdown 报告
python scripts/run_agent_evals.py --repeat-runs 3

# 与基线对比，回退即非零退出（适合接 CI）
python scripts/run_agent_evals.py \
  --baseline evals/reports/agent_eval_latest.json \
  --fail-on-regression --fail-on-failed-cases

8.2 为什么 Agent 不能只靠单测

断言字符串是最脆的测试

模型输出每次措辞都不同，assert "已生成" in response 这类断言只能证明「没崩」，证明不了「做对了」。项目改为断言结构化字段：intent 是否为 jd、steps 里是否有 confirm 且状态为 pending、artifacts 里是否有 requirements 类型。这些是稳定的，也是业务真正在意的。

09选型代价与技术债

任何选型都有代价。这一节把代价写清楚，比只写优点有用——接手的人需要知道哪里会疼。

代价具体影响建议
请求级图重编译 AgentGraphService.__init__ 每次请求都 build_graph()；get_shared_graph() 已定义但未使用 按 checkpointer 缓存编译结果，或启用共享图；图构建是纯 CPU，但节点多时仍有开销
chat 模型缺生产配置 get_chat_model() 未设 request_timeout / max_tokens / recursion_limit，路由模型已补齐 与路由侧对齐，尤其是 create_agent 的递归上限，避免工具循环跑飞
记忆靠文本注入 每轮拼最近 12 条、截断 6000 字符；长会话早期上下文丢失 引入摘要或分层记忆；当前方案的问题在超长会话才暴露
降级不可观测 legacy.py 的宽 except 只打 warning，没有计数与告警 加降级计数、request_id 贯穿、Prometheus 指标；否则「模型一直失败但没人知道」
无链路追踪 缺 LangSmith / OTel tracing，token 用量与每轮工具耗时未记录 先接 OTel，再谈成本优化；没有数据无法判断优化点
checkpoint 表无清理策略 长会话状态持续增长，checkpoint_blobs 会变大 按 thread 最后访问时间做归档或清理；上线前定策略
双连接池占用 asyncpg 池 + psycopg 池各自 max_size=10，多实例易撞 max_connections 部署时按「实例数 × 20」核算，必要时调小 checkpointer 池
最需要警惕的一条

模型路由已成为默认路径。规则未命中的消息都会走一次工具循环，延迟与调用量都高于纯规则。AGENT_ROUTER_MODE=rule 是应急开关，但它会让所有模糊表达退化到关键词匹配。上线后要盯两个指标：路由平均耗时、路由回退率。回退率突然上升，通常意味着模型侧出了问题，而不是用户说话方式变了。
