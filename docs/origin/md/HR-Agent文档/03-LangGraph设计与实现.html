00迁移目标与兼容边界

0.1 迁移前的问题

迁移前，HR Agent 是纯手写编排：入口 AgentService.chat()，由 agent_service.py 加三个 mixin 组成，约 5800 行。意图识别、受控 ReAct 决策、工具选择、SSE 事件、人工确认全部手写，业务逻辑（JD、评分标准、简历、面试、试卷、删除、邮件）与编排逻辑混在同一个 service 里。

后果不是「跑不起来」，而是改不动：加一个确认步骤要动四五个地方；评测只能测到最终字符串；确认流程靠前端把 confirmed_requirements 再发一次，跨请求的状态靠消息表双写维持。

迁移前

单函数 + 条件分支 → 工具调用 → 返回响应。
状态：service 实例属性 + 消息表。
确认：返回 requires_confirmation，前端回传。
流式：手写 async generator 逐段 yield。

迁移后

主图路由 + 意图子图。
状态：AgentState + PostgreSQL checkpoint。
确认：interrupt() 暂停，Command(resume=) 续跑。
流式：astream(updates+custom) 映射为 SSE。

0.2 四条不可破坏的契约

迁移期间最怕的不是写不出来，而是「顺手改了对外接口」。以下四项在迁移中保持不变，是这次改造能安全落地的原因：

契约位置约束
chat() 签名services/agent_service.py评测进程内调用，参数与返回不可变
AgentChatResponseschemas/agent.pyintent / route / steps / artifacts / requires_confirmation / missing_fields 不变
评测用例evals/agent_cases/*.json零改动；step id、artifact type 有硬断言
SSE 事件词汇前端 consumeAgentStreamdelta / progress / artifact / final 兼容旧语义
迁移策略

用「绞杀者模式」：新图先跑通一条链路（JD 确认流），旧入口保留并指向新图；等评测集全绿，再逐条把意图搬到子图。整个过程对外只有一个入口，随时可回退。这不是技术洁癖，是为了让业务方在迁移期间感觉不到系统在换引擎。

1.2 分层调用关系

为什么不把 db session 放进 state

AsyncSession 不可序列化，而 checkpoint 会把 state 写进 PostgreSQL。所以 db、user_id、agent_service 一律通过 RunnableConfig["configurable"] 传递。这条规则如果破坏，第一次 interrupt 就会在序列化阶段炸掉。

02主图结构

build_graph(checkpointer) 构建的是一张「分发图」：主图只做路由，每个意图是独立编译的子图，compile() 之后作为节点挂进主图。子图与主图共用 AgentState schema，channel 值自动透传。

backend/app/agent/graph.py · 条件边
def _after_jd_confirm(state):
    # confirmed_requirements 非空 = 用户已确认（interrupt resume / 兼容回传），继续执行；
    # 否则 jd_confirm 本轮产出的是确认请求响应，直接结束。不读 final_response：
    # checkpoint 跨轮残留的旧值会误判
    if state.get("confirmed_requirements"):
        return "jd_execute"
    return END
这个注释值钱

最初的条件边是判 final_response 是否存在。问题在于 checkpoint 会跨轮保留上一轮的值，新一轮进来时旧 final_response 还在，条件边就会误判成「已结束」。改成判 confirmed_requirements 才是本轮语义。这类 bug 只在多轮会话里出现，单轮测试发现不了。

03状态设计

AgentState 有 27 个字段，分组后其实只有六类。设计上的关键决策不在字段多少，而在哪些字段跨轮累积、哪些每轮覆盖。

3.1 字段分组

分组字段说明
输入user_message · attachments · confirmed_requirements · auto_execute · conversation_id每轮写入
路由intent · route · agent_plan · memory_context · dest_node由 route_intent 产出
过程steps普通 channel，每轮覆盖
产物artifactsAnnotated[..., add_artifacts] 跨轮累积，最多 50 条
终态final_response完整 AgentChatResponse.model_dump()
中间态parsed_requirements · jd_missing_fields · jd_interrupt_payload · edit_* · delete_*仅子图内部使用，同轮互斥共用
直通preset_intent文件流端点跳过路由决策

3.2 artifacts 的跨轮累积

「改改刚才那个 JD」能工作，靠的就是这个 reducer。默认 channel 是「后写覆盖」，这里换成「追加 + 保留最近 50 条」：

backend/app/agent/state.py
def add_artifacts(left, right):
    """artifacts 累积 reducer：跨轮保留全部产物，供编辑/删除链路反查。"""
    merged = list(left or [])
    for item in (right or []):
        merged.append(item)
    # 只保留有限条数，避免长会话 checkpoint 膨胀
    return merged[-50:]

class AgentState(TypedDict, total=False):
    artifacts: Annotated[List[Dict[str, Any]], add_artifacts]

3.3 三个关键决策

不用 add_messages

会话连续性靠每轮注入 memory_context 文本，而不是让 LangGraph 累积消息。原因：与旧文本记忆语义冲突，且 checkpoint 会无限膨胀。

db / user 不进 state

AsyncSession 不可序列化，统一走 configurable。state 里只放可 JSON 化的数据。

steps 每轮覆盖

意图节点产出完整 step 列表，评测按 step id / status 断言。累积会导致上一轮的步骤混进本轮界面。

跨轮残留是这套设计的主要 bug 来源

新消息进来时，必须显式清零 agent_plan、preset_intent、final_response。否则 route_intent 会复用上一轮 checkpoint 里的计划（例如上轮 intent=jd），直接跳过本轮意图决策。这段清零逻辑写在 bridge.run_stream() 里，注释也标了原因：

# 新消息必须显式清零跨轮残留的 channel
invoke_input = { ..., "agent_plan": None, "preset_intent": preset_intent, "final_response": None }

04路由决策

路由是整个系统的入口判断，也是成本最敏感的地方——每条消息都要过一次。方案是两级：规则快通道（毫秒级、零模型调用）优先，判不出来再走观察型 ReAct（可调只读工具，再输出结构化决策）。

4.1 route_intent 节点流程

4.2 规则快通道

规则不是「if 关键词」，它用三类特征组合判断，命中即返回，不进入模型：

特征例子作用
关键词删除 / 删掉 / 移除 / 清理 + 资源名词优先识别高危动作，避免被别的意图抢走
附件格式pdf/doc/docx/txt/md + 评分、筛选、简历「上传了简历说要评分」直接判 resume_screening
上一轮产物artifacts 里有 JD，说「改一下」判断这是不是「改刚才那个」，走 jd_edit
规则顺序是有讲究的

删除规则必须排在通用意图之前，否则「删掉刚才那个 JD」里的「JD」会让它被判成 jd。反过来，继承删除候选的规则必须排在通用意图之后，否则「生成一个 JD：张三」这种含候选名的正常请求会被抢进删除流程。这个先后顺序在 reasoning.py 里有明确注释。

4.3 观察型 ReAct 路由

规则判不出来时，交给一个「只选路、不写数据」的 agent。它可以先调用 search_resources 观察当前用户最近的资源（JD、评分标准、简历、面试、试卷），再输出结构化决策。

4.4 结构化决策的约束

backend/app/agent/routing_agent.py
class RouterDecision(BaseModel):
    mode: Literal["chat", "tool"]
    action: Literal["chat", "use_tool", "ask_user"]
    intent: str = Field(..., min_length=1)
    thought: str = Field(..., min_length=1)      # 一句推理摘要，不展开内部推理
    observation: str = ""
    confidence: Optional[float] = Field(None, ge=0.0, le=1.0)
    reply: Optional[str] = None

    @model_validator(mode="after")
    def _check_action_mode(self):
        expected = "chat" if self.action == "chat" else "tool"
        if self.mode != expected:
            raise ValueError(f"mode={self.mode} 与 action={self.action} 不一致")
        return self

这个 validator 看着像小题大做，实际拦住了一类真实错误：模型输出 mode=chat 但 action=use_tool，下游按 mode 分支就会当成闲聊，用户的任务被静默丢弃。结构化输出不等于语义自洽，得自己校验。

4.5 回退链

触发条件行为plan.source

LLM_API_KEY 未配置跳过 ReAct，走关键词规则fallback

05意图子图

每个意图都是独立编译的子图，compile() 后当节点挂进主图。子图类型只有四种：确认式（jd / skill）、多步编辑（edit / delete）、单步准备（planning）、文件直通（exec）。

5.1 JD：三个节点，一次确认

5.2 为什么把解析和确认拆成两个节点

LangGraph 的 interrupt 语义

interrupt() 恢复时，节点内此前的状态写入会被丢弃，整个节点从头重跑。如果把「LLM 解析需求」和「interrupt 等待确认」放在同一个节点：resume 后解析会重跑一次，模型输出可能与上次不同，用户确认的字段和最终执行的字段就对不上了。

拆开后：jd_prepare 完成解析并写入 state → jd_confirm 只做 interrupt → resume 时只重跑一个不含 LLM 的节点，结果稳定。

backend/app/agent/nodes/jd.py · jd_confirm
async def jd_confirm(state, config):
    if state.get("confirmed_requirements"):
        return {}                       # 已是确认回传轮，空过

    payload = state.get("jd_interrupt_payload") or {}
    if not config.get("configurable", {}).get("thread_id"):
        # 兼容门面（无 checkpointer / 评测）：以普通响应结束本轮
        return {"final_response": {**payload, "requires_confirmation": True}, ...}

    # 有 thread_id：真暂停，resume 值即旧 confirmed_requirements 结构
    resume_value = interrupt(payload)
    return {"confirmed_requirements": resume_value if isinstance(resume_value, dict) else {}}

判定条件是 configurable.thread_id 是否为空，而不是 checkpointer 是否存在。评测用例不传 conversation_id，所以自然走兼容分支，不会卡在 interrupt 上。

5.3 Skill：两个节点，响应式确认

邮件类 Skill 不用 interrupt，而是把确认表单作为新消息再发一次。原因很实际：前端已经在用「确认卡 + 重新提交」的交互，改成 interrupt 要同时改 UI 与消息落库逻辑，收益不足以支撑这次改动。

节点行为
skill_draft生成邮件草稿 + 确认 artifact，写 final_response 结束本轮。若本轮是确认回传轮（confirmed_requirements 非空），空过
skill_sendconfirmed_requirements.action 命中 send_email 后执行发送

条件边因此写成「confirmed_requirements 非空 → skill_send，否则 END」。与 JD 的条件边同构，但语义不同：JD 是 resume 带回来的值，Skill 是新消息带进来的值。

5.4 多步编辑：完成即终止

编辑与删除链路有四到三个节点，但不是每个节点都必须走完。缺修改要求、多候选、资源定位失败时，应该停下来问，而不是继续往下执行写操作。

backend/app/agent/graph.py
def _sequential_subgraph(steps, end_after):
    builder = StateGraph(AgentState)
    for name, node_fn in steps:
        builder.add_node(name, node_fn)
    builder.add_edge(START, steps[0][0])
    for index, (name, _) in enumerate(steps):
        if name not in end_after:
            builder.add_edge(name, steps[index + 1][0])   # 不可终止：直接连下一节点
            continue
        nxt = steps[index + 1][0]
        builder.add_conditional_edges(
            name,
            lambda state, nxt=nxt: END if state.get("final_response") else nxt,
            {nxt: nxt, END: END},
        )
    return builder.compile()

5.5 单步准备与文件直通

单步 prepare

interview_plan / exam_generate / resume_screening 在图上只有一个节点：解析需求、算缺失字段、给出引导。真正执行不在图里，由前端调用专用端点（带文件）触发 preset_intent 直通。

原因：这些任务需要上传文件，走图反而多一次转发；而对话入口只负责「告诉他下一步去哪」。

文件直通

resume_exec / interview_exec / exam_exec 复用旧的流式生成器，事件通过 get_stream_writer() 透传。入口带 preset_intent，跳过路由决策——避免大文件上传后再多跑一次模型。

一条链路两种入口：对话入口和文件流入口走同一张图，后者只是抄近道。

06人工确认机制

三种确认模式并存，按意图选择。这不是历史包袱，而是按交互形态做的匹配：确认内容不同，前端呈现方式就不同。

意图机制说明
jd LangGraph interrupt + Command(resume=) HTTP 路径 thread_id 非空，jd_confirm 暂停图；前端 POST /agent/graph/resume 恢复。resume 值即旧 confirmed_requirements 结构
email_notification 等 skill 不开 interrupt 前端把确认表单作为新消息再发一次 graphChat；路由识别 confirmed_requirements.action 后直通 skill_send，skill_draft 自动跳过
jd_edit / criteria_edit / resource_delete 同轮多节点 + 引导响应 多候选、缺修改要求、缺资源类型时直接产出 final_response 结束本轮，由用户补充信息后开启下一轮

6.1 恢复流程

有 checkpointer（正常路径）

图停在 jd_confirm，state 写入 checkpoint。前端拿到 interrupt 事件与 thread_id，渲染确认表单；提交时 POST /agent/graph/resume，后端以 Command(resume=value) 继续，图从断点往下走到 jd_execute。

无 checkpointer（评测 / 兼容）

不能 interrupt。jd_confirm 检测 thread_id 为空，直接返回 requires_confirmation=True 的普通响应；前端按旧契约回传 confirmed_requirements，走 /agent/stream 带 preset_intent=jd 执行。

为什么这个兼容分支值钱

评测集不传 conversation_id，因此天然走兼容分支，不会卡在 interrupt 上等到超时。这意味着同一张图既能跑交互式确认，又能跑无状态批处理，评测与生产共用一套代码路径，测出来的结果才有意义。

6.2 前端对接要点

  • agentThreadId 与 conversation_id 同值，从 SSE 事件的 thread_id 更新。
  • 普通对话走 graphChat；JD 确认在 useResume && agentThreadId 时走 graphResume，否则回退旧 /agent/stream。
  • 确认卡提交时把 confirmed_requirements 作为 value 传给 resume；邮件确认则作为新消息再次 graphChat。
  • final 事件仍完整落库到 conversation message，保证刷新后可恢复。

07持久化与记忆

7.1 Checkpointer

AsyncPostgresSaver 使用独立的 psycopg_pool.AsyncConnectionPool（业务侧仍是 asyncpg，两套池并存）。应用启动时 init_checkpointer() 执行幂等 setup() 建表，关闭时释放池。

backend/app/agent/checkpoint.py
_pool = AsyncConnectionPool(
    conninfo=settings.DATABASE_URL,
    min_size=1,
    max_size=settings.DATABASE_POOL_SIZE,
    kwargs={"autocommit": True, "prepare_threshold": 0},
    open=False,
)
await _pool.open(wait=True, timeout=30)
_checkpointer = AsyncPostgresSaver(_pool)
await _checkpointer.setup()      # 幂等建表：checkpoints / blobs / writes / migrations
初始化失败会阻止应用启动

main.py lifespan 里 init_checkpointer() 抛异常会导致启动失败。这是有意的：checkpointer 不可用时，所有确认类功能都会退化，与其带病运行，不如启动就报错。

7.2 记忆

build_conversation_memory() 读取最近 12 条消息（多取 3 条用于过滤当前消息），拼成「用户: … / 助手: …」文本，每段截 900 字符，总长截到 6000 字符。

用途为什么需要记忆
路由决策「上次那个」需要历史才能判断指向
chat 对话作为额外 SystemMessage 注入，子图本身不持久化消息
需求解析多轮补全字段时，后一轮要能看到前一轮说了什么
编辑定位「改成 3 年经验」要知道改的是哪个 JD

截断取尾部而非头部：近期上下文比早期更重要。代价是长会话早期信息会丢，这是已知限制。

7.3 产物反查

优先级来源场景
1state.artifactscheckpoint 跨轮累积；route_intent 注入到 service 的 _graph_artifacts
2Message.context.agent_response图状态为空时回退；兼容旧前端双写路径

这样「改改刚才那个 JD」「删掉刚才那个」在 thread 内可以直接从图状态定位，不依赖前端双写是否成功。等阶段 4 清理完成后，第二优先级可以下线。

08流式事件契约

bridge.run_stream() 用 astream(stream_mode=["updates","custom"], subgraphs=True)，把图的事件流映射成前端认识的 SSE。

8.1 三个容易出错的地方

01双 final

节点内如果发了 final custom 事件，bridge 会丢弃它。终态统一从流结束后的 state.final_response 产出，否则前端会落两次库。

02子图命名空间

ns 非空时要拼成 jd_edit:locate。前端步骤条按这个名字匹配，拼错就只显示「执行中」不显示具体步骤。

03伪流式

整轮没有真实增量时，_stream_text() 按 6 字符切分 final.message 模拟流式，保持旧前端体验。这是兜底，不是常态。

8.2 事件载荷

10评测与回归

评测层是这次迁移的事实回归边界。它的设计有个巧思：走的是同一条代码路径，但不是同一个运行形态。

怎么跑

agent_eval_runner._call_agent() 在进程内构造 AgentService(db)，调用 chat()。因为 chat() 委托给不带 checkpointer 的共享图，且用例不传 conversation_id，所以不会触发 interrupt 分支。

校验什么

intent、route、requires_confirmation、missing_fields、steps（id/status）、artifacts（type），以及响应签名稳定性。不断言自然语言字符串——那是模型措辞，不是行为。

10.2 为什么评测能绕过 interrupt

判据是 thread_id，不是 checkpointer

如果判据写成「有没有 checkpointer」，评测环境一旦配上 checkpointer 就会卡在 interrupt 上等超时。改成判 configurable.thread_id 为空，评测用例天然不传 conversation_id，就自动走兼容分支——行为正确，而且不需要为测试写开关。
