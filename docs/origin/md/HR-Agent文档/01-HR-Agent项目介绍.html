HR Agent 项目介绍

一个以自然语言对话为入口的智能人力资源工作台。用户不必在菜单与表单之间跳转，只需说明目标，系统识别意图、调度受控工具、在关键动作上停下来等确认，再把结构化产物落回业务表。

00一页速览

HR Agent 不是「给 HR 用的 ChatGPT」，也不是完整的人力资源信息系统。它的准确定位是：把 HR 高频、低结构化的文本工作，沉淀成可执行、可确认、可回溯的业务链路。

是对话即操作

一个统一入口承接 JD 生成、简历筛选、面试方案、试卷生成、邮件通知、资源删除。用户说目标，系统选工具。

是受控编排

模型只负责选路；删除、发送、落库这些写操作交给确定性节点。关键动作在图上是真暂停，不是提示词劝告。

不是自动决策

不做自动录用、自动淘汰、自动群发。AI 产出是初稿与辅助判断，最终结论由 HR 负责，这是写进需求文档的边界。

核心链路只有三步：听懂要做什么 → 选对工具 → 该停的地方停下来。前两步靠两级路由（规则快通道 + 观察型 ReAct），第三步靠 LangGraph 的 interrupt 与 PostgreSQL checkpoint。

01业务背景

1.1 组织处境

企业 HR 团队的工作有一个共同特征：输入是零散的自然语言，输出是结构化文档，中间大量环节依赖人的阅读与改写。业务部门一句「帮我招个前端，能带团队的」，到一份可发布的 JD，中间要补齐职责、要求、技能、薪资区间、汇报关系；一份简历到「要不要约面」，中间要读完项目经历再和 JD 逐条对齐。

这些环节单看都不难，难在量大、重复、口径不稳定。招聘旺季 HR 一天要过几十份简历，判断标准会随疲劳漂移；同一个岗位换一位 HR 写 JD，结构和侧重就变了。培训侧同理：一套培训资料要出成试卷，出题人得先通读一遍再逐题设计，耗时且难复用。

1.2 业务链路上的六个断点

把招聘与培训的主链路摊开看，AI 能介入的位置并不是均匀分布的。真正卡住的不是「写不出来」，而是六处信息在人与人之间转手时的损耗。

1.3 立项动因

业务侧

招聘需求量增长但 HR 编制有限，初筛与文档产出占了大量本可用于沟通和判断的时间。企业希望先提升「产出效率」，而不是先上重型 HRIS。

技术侧

大模型的文本理解与生成能力已经能覆盖 JD、评分标准、面试题、试卷这类结构化写作；RAG 让企业制度问答有了可引用的依据；Agent 编排让「一句话触发一条业务链」变得可行。

组织侧

企业希望把大模型能力落在明确业务流程里，而不是停留在通用聊天工具。HR 是理想的试点域：场景高频、边界清楚、失败可回退到人工。

落地侧

项目可从内部试点起步，不必一次性替换现有 ATS/HRIS。JD、简历、考试三条主流程各自独立，任一环跑通都能独立产生价值。

1.4 基线数据的采集口径

立项时要能量化收益，前提是有基线。以下六项建议在试点前采集，缺历史数据就先记 2–4 周。

指标采集方式用途

02核心痛点分析

痛点要分三层看：业务痛点决定值不值得做，产品痛点决定做成什么形态，技术痛点决定能不能稳定跑起来。三层不对齐，项目就会变成「演示很惊艳、上线没人用」。

2.1 三层痛点

层级具体表现本质问题
业务 JD 从需求到可发布要反复补问；简历靠人工读，标准不稳；面试方案与评分标准因人而异；培训出题重复劳动；制度文档检索成本高 文本处理工作没有沉淀成可复用的生产能力，每次都从零开始
产品 能力分散在脚本、外部工具、个人经验里；没有统一登录、权限、历史记录；新用户要理解菜单、字段、操作顺序 缺少统一入口与统一数据底座，AI 能力无法变成产品
技术 LLM、工作流、RAG、文件解析、向量检索、业务库各说各话；长任务无进度反馈；关键动作无法确认与回滚 缺少状态化编排与人机协同机制，AI 只能做一次性问答

2.2 从痛点到系统能力

下图把「看到的症状」推到「根因」，再对到「系统里具体哪一层解决」。这张图是后续所有设计决策的来源：凡是落不到第三列的需求，都不进范围。

2.3 痛点优先级

下表是定性评估，不是实测数据。判据是三个：发生频次、影响面、可自动化程度。三个都高的先做。

痛点频次影响面可自动化优先级
简历初筛耗人力、标准不稳极高招聘全流程高（可评分可排序）P0
JD 与评分标准从零撰写高招聘起点高（文本生成）P0
面试方案因人而异高面试质量高（结构化生成）P0
培训出题重复劳动中培训闭环高（资料→题目）P0
制度知识靠人找人高全员中（依赖资料质量）P0
面试评价无证据、不可复核中录用决策中（依赖转写质量）P1
通知邮件手工写、易漏发中候选人体验中（需人工确认）P1
招聘培训进展不可视中管理决策高（统计聚合）P1
最容易做错的三件事

一、把「生成」当「决策」。简历评分再准也只是排序建议，写进产品文案和 UI 时必须保留「待复核」状态，否则业务方上线第一天就会质疑责任归属。

二、用提示词约束代替机制约束。「请不要自动发送邮件」写在 system prompt 里，模型换个说法就可能绕过去。正确做法是把发送动作放在图上的独立节点，前面加 interrupt。

三、一开始就做通用 Agent。开放式工具调用看着强，实际每次误触发都要人工收拾。项目最终选择「动作空间受限 + 写操作不进模型」，这是被现实教育出来的结论。

3.4 招聘主流程

五步闭环，每一步的产出都是下一步的输入。这条链路决定了数据模型的骨架：JD → 评分标准 → 简历评估 → 面试方案 → 面试记录，五张表以外键串起来。

3.5 Agent 对话流程

对话入口不是「聊天框 + 几个按钮」，它需要能判断三件事：这是闲聊还是任务、任务缺什么、该走哪条链。判断结果直接决定响应结构。

01归一化附件文件名、扩展名、大小标准化，供意图判断使用
02识别意图规则快通道优先，未命中再走观测型 ReAct
03判断动作chat / use_tool / ask_user 三选一
04调度工具只调用 tool_registry 声明过的能力
05确认后执行写操作在确定性子图里完成
06流式回传progress / delta / artifact / final

响应契约

字段含义
message给用户看的自然语言回复
intent / route识别到的意图，以及建议跳转的业务页面
steps执行步骤列表，含 id、标题、状态、工具名
artifacts结构化产物：JD、需求、评分结果、面试方案、试卷
suggestions下一步建议
requires_confirmation是否需要用户确认后才继续
missing_fields缺失的前置条件，配合表单回填
设计取舍

这套契约从手写编排时代就定下来了，迁移到 LangGraph 时一字未改。原因是评测用例对 step.id 与 artifact.type 有硬断言，且前端事件解析依赖字段名。编排引擎可以换，对外契约不能换。

04技术选型

本节给结论，详细论证与对比见《02 技术栈与选型思路》。选型不是挑最新最热的组件，而是在「团队能维护」与「场景撑得住」之间找交点。

4.1 五条原则

01业务优先

按 HR 实际工作流组织系统，而不是为了展示 AI 能力堆功能。

02受控自动化

AI 负责生成、分析、路由；最终决策与对外动作保留人工。

03分层解耦

前端、API、Service、Model、外部 AI 服务边界清晰，任一环可替换。

04可追踪

关键产物落结构化表，可查询、复用、删除，不留在会话里。

05可回退

每个 AI 环节失败都有降级路径：模型不可用退规则，Rerank 失败退原排序。

隐性的第六条

不引入团队没有运维能力的中间件。少一个组件，就少一类半夜报警。

4.4 四个关键取舍

LangGraph vs 手写编排

选手写：5800 行 service 加 3 个 mixin，意图、工具、确认、SSE 全揉在一起。选 LangGraph：把状态、路由、中断、事件四件事交给框架，业务函数原样保留。代价是多一层抽象与一个 checkpointer 依赖。

pgvector vs 专用向量库

选 pgvector：数据量在十万级、检索与业务表强关联（按知识库过滤、按用户隔离），SQL 里一个 JOIN 就能解决。换成 Milvus 要多维护一套集群，收益在这个量级体现不出来。

Dify + 自研双轨

不是二选一。长文本生成类（JD、评分标准、试卷、简历解析）放 Dify，改了即时生效；编排、确认、权限、落库必须自研，因为需要事务与可回滚。

SSE vs WebSocket

选 SSE：生成任务是「客户端请求、服务端持续回吐」，没有双向需求。SSE 走普通 HTTP，鉴权头、负载均衡、日志都按现成方式处理。

4.5 架构上的三个「不」

这三条是硬约束，不是建议

一、写操作不进模型。删除、发送、落库全部由确定性节点执行。路由 agent 只持有 search_resources 一个只读工具，模型只能在 chat / use_tool / ask_user 里选。

二、路由阶段不写数据。「选路」与「执行」分离，模型判断错最多走错分支，不会误删记录。

三、对外动作必须确认。邮件发送在图上有独立的 interrupt 节点，没有 checkpointer 时退化成 requires_confirmation 响应，任何路径都绕不过去。

05业务价值与 ROI

5.1 四类价值

效率

JD、评分标准、面试题、试卷的初稿时间被压缩；简历批量评分替代逐份阅读；文档检索变成问答。

质量

JD 与评分标准结构统一；候选人评价从「总分」变成「维度 + 理由 + 证据」；知识问答带引用来源。

管理

用户、角色、文档、对话、评估结果、考试结果进入统一系统；统计看板提供运营概览。

体验

对话入口降低新用户理解菜单的成本；流式输出让等待有反馈；业务页面保留编辑与确认空间。

5.2 ROI 测算口径

ROI 不能只用「AI 是否生成了内容」衡量，要看流程节省 + 质量提升。以下为测算模板，需替换为企业真实数据。

价值项计算口径
JD 生成岗位数 × 人工初稿耗时 − AI 辅助后编辑耗时
简历初筛简历数 × 人工初筛耗时 − AI 批量评分与复核耗时
面试准备面试人数 × 人工准备耗时 − AI 方案编辑耗时

5.4 成功标准

功能

登录与权限可用；JD/评分/简历/面试/知识库/试卷六条链路可各自走通；Agent 能识别常见任务并返回结果或追问。

质量

接口在缺失参数、无权限、资源不存在时返回明确错误；长任务有流式反馈；敏感接口经过认证与权限校验。

验收

3 类岗位端到端验证；2 份企业资料完成知识问答；1 份培训资料完成考试闭环；管理员完成用户、角色、邮箱配置。

06边界与风险

6.1 明确不做的事

  • 不做完整 ATS：渠道投放、候选人 CRM、Offer 审批、入职办理均不在范围。
  • 不做完整 HRIS：薪酬、绩效、考勤、组织架构全生命周期不在范围。
  • 不承诺自动决策：AI 不自动录用、不自动淘汰、不自动发送不可撤销的通知。
  • 不内建企业平台能力：CI/CD、集中日志、服务发现、灰度发布属于上线环境职责。

6.2 五类风险与缓解

风险表现缓解措施
模型输出不稳定 同一份转写重复评分出现分数漂移；结构化输出偶尔缺失 固定采样种子 + 温度 0；结构化决策缺失时按次数重试，仍失败回退规则；提供漂移测量脚本
文档解析质量 扫描件、乱码、复杂表格导致提取失败或错位 明确提示解析失败并允许重传；不基于失败文本生成虚假评分；多解析器按格式选型
敏感数据合规 简历、候选人信息、面试录音属敏感个人信息 权限隔离、明确保存期限与删除流程；对外部模型调用范围做书面约定；日志脱敏
外部服务依赖 LLM、Dify、Embedding、Rerank、会议 API 任一不可用都会影响体验 逐项降级：Rerank 失败退原排序、LLM 失败退规则、Dify 超时提示重试并保留输入
组织接受度 HR 担心被替代，或过度信任 AI 结论 产品定位写成「初稿 + 人工确认」；UI 保留待复核状态与修改入口；不隐藏 AI 参与痕迹

6.3 合规红线

三条不可越过的线

一、AI 评分不得作为淘汰或录用的唯一依据。系统输出的定位是辅助判断，最终决定必须有人签字负责。

二、候选人敏感信息不得明文外泄。日志、导出、前端回显都要脱敏；邮箱授权码不得明文回显。

三、对外沟通不得绕过确认。邮件发送前必须由 HR 确认收件人、主题、正文，且发送失败不得自动重试造成重复发送。

07落地路线

项目按「先验证可行性，再补编排与治理，最后接企业平台」四段推进。每个版本都有可独立交付的价值，不依赖下一版才能用。

MVP
验证核心业务可行性 登录、JD、评分标准、简历评分、知识库、试卷生成。目标是证明「AI 初稿可用」，不追求覆盖率。
V1.0
形成可试点的内部工作台 Agent 编排、面试方案、考试管理、系统管理、统计看板。此时 Agent 从「手写编排」迁到 LangGraph，确认机制与流式事件成型。
V1.1
提升业务连续性 邮件通知 Skill、更多导出能力、权限细化、错误体验优化、面试评价 AI 链路与人工修订。
V2.0
进入企业集成阶段 招聘渠道、审批流、组织架构、企业 SSO、审计日志。此阶段开始与既有 HRIS/ATS 对接。
