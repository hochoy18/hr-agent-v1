# 方案设计文档

## 1. 设计目标

方案设计目标是将 HR 招聘、培训、知识问答和系统管理需求落到可实现的应用架构中。系统采用前后端分离、后端分层服务、关系数据库 + 向量检索、LLM/Dify 工作流集成、受控 Agent 编排的方式实现。

设计原则：

- 业务优先：围绕 HR 实际工作流组织功能，而不是单纯展示 AI 能力。
- 受控自动化：AI 负责生成、分析、建议和路由，不直接替代人工做最终决策。
- 分层解耦：前端、API、Service、Model、外部 AI 服务分层清晰。
- 可追踪：关键产物保存为结构化记录，便于查询、复用和删除。
- 可扩展：新增工具可通过 Agent 工具注册表或 Skill 机制接入。

    U["用户/HR/管理员"] --> FE["Vue 3 前端"]

### 3.3 前端鉴权

- 路由 `meta.requiresAuth` 控制需要登录的页面。
- Pinia auth store 保存登录状态和 Token。
- Axios 请求统一携带 Token。
- 路由守卫负责未登录跳转。
- 后端权限校验是最终安全边界。

### 3.4 前端交互方案

- 普通 CRUD 页面使用 REST API。
- JD、试卷、Agent 等长文本或多步骤任务优先使用 SSE 流式接口。
- 文件上传页面校验格式和大小，并显示上传/处理进度。
- Agent 页面展示步骤、产物、建议、缺失字段和跳转路由。

### 3.5 前端状态管理

- 登录状态、Token 和用户信息由 Pinia auth store 管理。
- 业务页面以接口返回数据为准，不在前端保存不可恢复的业务状态。
- 长任务页面需维护“生成中、已完成、失败、可重试”等状态。
- 文件上传页面应区分上传成功、处理成功和 AI 评估成功，避免用户误解。

### 3.6 前端错误处理

- 401：清理登录状态并引导重新登录。
- 403：提示权限不足，不展示敏感操作入口。
- 422：展示字段级校验错误。
- 5xx 或外部服务失败：展示失败原因和重试入口。
- SSE 中断：提示任务中断，并允许用户重试或回到业务页面继续。

### 4.5 模块级详细设计

本节从模块内部说明输入、处理链路、服务协作、数据落点、输出和失败处理，作为研发实现、联调和测试设计的依据。

#### 4.5.1 认证与用户权限模块

模块目标：为系统提供登录、注册、当前用户识别、用户管理、角色分配和管理员权限控制。

| 设计项 | 说明 |
| --- | --- |
| 前端入口 | `Login.vue`、`Register.vue`、`UsersManagement.vue`、`RolesManagement.vue` |
| API | `/auth/*`、`/users/*` |
| Schema | `auth.py`、`user.py` |
| Service | `UserService`、`RoleService` |
| Model | `User`、`Role`、`UserRoleAssociation` |
| 安全依赖 | `get_current_user`、`get_current_superuser`、`get_current_admin_by_role` |

处理流程：

1. 用户注册或管理员创建用户时，后端校验用户名、邮箱和密码长度。
2. 密码通过 bcrypt 哈希后保存。
3. 用户登录时校验邮箱和密码，成功后签发 JWT。
4. 前端保存 Token，后续请求通过 `Authorization: Bearer <token>` 传递。
5. 后端依赖函数解析 Token，查询当前用户并校验是否启用。
6. 管理类接口继续校验超级管理员或角色权限。

失败处理：

| 场景 | 处理 |
| --- | --- |
| 邮箱或用户名重复 | 返回 409 或业务错误 |
| 密码不足 6 位 | 返回 422 |
| Token 缺失或无效 | 返回 401 |
| 用户停用 | 返回 400 或 403 |
| 非管理员访问管理接口 | 返回 403 |

设计约束：

- 前端路由守卫只做体验控制，权限边界必须以后端依赖校验为准。
- 生产环境必须替换默认 `SECRET_KEY`。
- 密码、Token、邮箱授权码不得写入普通日志。

#### 4.5.2 HR Agent 编排模块

模块目标：将用户自然语言输入转化为受控业务动作。当前实现已从「线性 if/else + 提示词约束」迁移为 **LangGraph 图编排**，流程边界由图的节点与条件边保证，而不是由提示词自行遵守。

| 设计项 | 说明 |
| --- | --- |
| 前端入口 | `HRAgent.vue` |
| API | `/agent/stream`、`/agent/*/stream`、`/agent/graph/chat`、`/agent/graph/resume` |
| Schema | `AgentChatRequest`、`AgentChatResponse`、`AgentStep`、`AgentArtifact` |
| 编排 | `app/agent/graph.py`、`app/agent/state.py`、`app/agent/bridge.py`、`app/agent/nodes/*` |
| Service | `AgentService`（门面 + 业务 handler）、`AgentGraphService`、`IntentService`、`AgentSkillDispatcher` |
| 依赖服务 | JD、简历评估、面试方案、试卷、邮箱 Skill、`search_resources` 只读工具 |

图结构：

```mermaid
flowchart TB
    S["START"] --> R["route_intent<br/>记忆构建 + 规则快通道 + 受控 ReAct"]
    R --> C{"条件边（dest_node）"}
    C -->|jd| JD["jd_prepare → jd_confirm(interrupt) → jd_execute"]
    C -->|jd_edit / criteria_edit| ED["parse → locate → rewrite → save"]
    C -->|resource_delete| DE["parse → resolve → execute"]
    C -->|skill（邮件等）| SK["skill_draft → skill_send"]
    C -->|interview_plan / exam_generate / resume_screening| PL["prepare 单步子图"]
    C -->|resume_exec / interview_exec / exam_exec| EX["文件流直通执行"]
    C -->|chat| CH["create_agent ReAct 工具循环"]
    JD --> E["END"]
    ED --> E
    DE --> E
    SK --> E
    PL --> E
    EX --> E
    CH --> E
```

设计要点：

| 设计项 | 说明 |
| --- | --- |
| 状态定义 | `AgentState` 为 TypedDict；`artifacts` 用自定义 reducer 跨轮累积（上限 50 条），`steps` 每轮覆盖 |
| 不可序列化对象 | `db`、`user_id`、`agent_service` 通过 `RunnableConfig["configurable"]` 传递，不进 checkpoint |
| 确认语义 | `jd_confirm`、`skill_send` 使用 `interrupt()` 真暂停；前端收到 `interrupt` 事件渲染确认卡片，确认后调 `/agent/graph/resume` 恢复 |
| 上下文记忆 | 路由节点先构建对话记忆（历史消息 + 产物摘要），再决策；编辑/删除链路优先读图状态 `artifacts`，回退到 `Message.context` |
| 词表变化 | ReAct 路由 agent 按「允许意图集合 + 工具说明」做缓存 key，新增 Skill 后自动重建 |
| 端点直通 | 文件流端点通过 `preset_intent` 跳过决策，直达执行节点，避免多余 LLM 调用 |
| 评测无状态 | 评测门面 `AgentService.chat()` 使用不挂 checkpointer 的图，避免线程状态残留 |

失败处理：

| 场景 | 处理 |
| --- | --- |
| 意图不明确 | 走 `chat` 节点普通回复，不误触发写操作 |
| 缺少前置条件 | 返回 `missing_fields`，并给出对应页面路由 |
| 工具执行失败 | `steps` 标记 failed，返回错误摘要，保留已上传材料 |
| 图未产出 `final_response` | 桥接层返回 `error` 事件，前端提示重试 |
| SSE 中断 | 前端展示中断并允许重试；图状态可恢复 |
| 删除/发送等高风险动作 | 图内确认节点强制确认，未确认不落库 |

设计约束：

- Agent 只能调用工具注册表与 Skill 目录声明过的能力。
- 路由只做选路，不执行写操作；删除、发送、落库由后续确定性链路执行。
- 不暴露模型完整内部推理，只输出一句业务判断摘要。
- 产物必须允许用户编辑、保存或确认。

#### 4.5.3 JD 生成与管理模块

模块目标：支持自然语言招聘需求解析、JD 生成、JD 保存、查询、更新、删除，并作为后续评分标准和简历评估的基础数据。

| 设计项 | 说明 |
| --- | --- |
| 前端入口 | `JDGenerator.vue` |
| API | `/hr-workflows/parse-requirements`、`/hr-workflows/generate-jd`、`/job-descriptions/*` |
| Schema | `JDGenerateRequest`、`JobDescriptionCreate`、`JobDescriptionUpdate` |
| Service | `DifyService`、`JobDescriptionService`、`RemoteServiceClient` |
| 存储 | 远程 HR 服务（`/api/v1/job-descriptions/*`），本系统不建表 |

处理流程：

1. 用户输入岗位需求，前端可调用需求解析接口填充表单。
2. 后端构造 Dify 工作流输入，调用 type=1 生成 JD。
3. 若 `stream=true`，后端通过流式响应返回生成片段。
4. 用户编辑 JD 后调用保存接口。
5. 后端通过 `RemoteServiceClient` 把 JD 写入远程 HR 服务，并回填远程返回的 `id`、状态与元数据。
6. 列表和详情接口用于历史查询、复用和后续绑定评分标准。

关键字段：

| 字段 | 说明 |
| --- | --- |
| `title` | JD 标题，保存必填 |
| `content` | JD 正文，保存必填 |
| `requirements` | 用户原始需求 |
| `skills` | 技能标签 |
| `status` | 草稿、启用、归档等状态 |
| `conversation_id` | 关联 Agent 或对话 |

失败处理：

| 场景 | 处理 |
| --- | --- |
| 需求为空 | 返回 422 或前端阻止提交 |
| Dify 超时 | 返回生成失败，保留用户输入 |
| 保存字段缺失 | 返回字段校验错误 |
| 查询不存在 JD | 返回 404 |
| 删除存在关联记录的 JD | 试点默认逻辑下线或软删除，不破坏关联数据 |

#### 4.5.4 评分标准模块

模块目标：基于 JD 生成结构化评分标准，为简历评估提供一致评分口径。

| 设计项 | 说明 |
| --- | --- |
| 前端入口 | `JDGenerator.vue`、`ResumeScreening.vue` |
| API | `/hr-workflows/generate-scoring-criteria`、`/scoring-criteria/*` |
| Schema | `ScoringCriteriaGenerateRequest`、`ScoringCriteriaCreate`、`ScoringCriteriaUpdate` |
| Service | `DifyService`、`ScoringCriteriaService`、`RemoteServiceClient` |
| 存储 | 远程 HR 服务（`/api/v1/scoring-criteria/*`），本系统不建表 |

处理流程：

1. 用户选择或生成 JD。
2. 前端提交 JD 内容和岗位标题。
3. 后端调用 Dify type=2 生成评分标准。
4. 用户审核维度、权重、总分和说明。
5. 保存评分标准，并可绑定 `job_description_id`。
6. 简历评估时可选用该评分标准。

数据设计：

| 字段 | 说明 |
| --- | --- |
| `title` | 评分标准标题 |
| `content` | 评分标准正文 |
| `total_score` | 总分，默认 100 |
| `scoring_dimensions` | 维度化评分结构 |
| `job_description_id` | 关联 JD |

失败处理：

| 场景 | 处理 |
| --- | --- |
| JD 内容为空 | 前端阻止生成或后端返回 422 |
| Dify 返回非结构化内容 | 保存正文，结构化维度为空或提示用户修正 |
| 权重口径不一致 | 前端提示人工确认 |
| 删除评分标准 | 删除前二次确认，不影响已有评估历史展示 |

#### 4.5.5 简历评估模块

模块目标：支持简历文件上传、文本提取、关联 JD、调用 AI 评估、保存评估结果、历史查询、状态更新和导出。

| 设计项 | 说明 |
| --- | --- |
| 前端入口 | `ResumeScreening.vue` |
| API | `/resume-evaluation/evaluate-auto`、`/hr-workflows/evaluate`、`/resume-evaluation/history` |
| Schema | `ResumeEvaluationResult`、`ResumeEvaluationResponse` |
| Service | `ResumeEvaluationService`、`DifyService` |
| Model | `ResumeEvaluation` |
| 文件依赖 | PDF/DOC/DOCX/TXT 解析能力 |

处理链路：

```mermaid
flowchart TB
    A["上传简历文件"] --> B["校验格式和大小"]
    B --> C["读取文件内容"]
    C --> D["提取文本"]
    D --> E["查询关联 JD/评分标准"]
    E --> F["调用 Dify type=3 或评估服务"]
    F --> G["解析候选人信息和评分维度"]
    G --> H["写入 ResumeEvaluation"]
    H --> I["返回总分、维度、理由和简历内容"]
```

输入输出：

| 类型 | 内容 |
| --- | --- |
| 输入 | 简历文件、`job_description_id`、可选 `scoring_criteria_id`、`conversation_id` |
| 输出 | 候选人信息、总分、维度评分、评分理由、简历文本、评估 ID |
| 入库 | 文件名、文件类型、简历文本、候选人字段、评分结果、关联 JD 和用户 |

失败处理：

| 场景 | 处理 |

#### 4.5.11 智能面试模块

模块目标：把「面试方案」推进到「面试评价」闭环——为候选人在腾讯会议开会、拿到逐字稿、配对问答、按规则与 rubric 打分、允许人工修订并留痕。

| 设计项 | 说明 |
| --- | --- |
| 前端入口 | `SmartInterview.vue`（简历预览 / 面试方案 / 面试记录 三个 Tab） |
| API | `/meetings/*`、`/interviews/*`（建会、同步、取消、上传材料、拉取转写、分析、评价查询与修订） |
| Service | `MeetingService`、`InterviewService`、`TranscriptionService`、`TranscriptSegmenter`、`QAPairing`、`ResumeEvaluationService` |
| Model | `Interview`（`interviews` 表） |
| 规则源 | `app/rules/interview_rules_v1.json`（`rule_version` 写入评价结果） |
| 外部依赖 | 腾讯会议 MCP、DashScope ASR、系统 `ffmpeg`、LLM |

处理链路：

```mermaid
flowchart TB
    A["选择候选人 + 会议参数"] --> B["MeetingService 建会"]
    B --> C["回写 meeting_id / code / join_url"]
    C --> D{"材料来源"}
    D -->|本地上传音视频| E["TranscriptionService：ffmpeg 抽音频 → ASR"]
    D -->|上传文档| F["解析文档文本"]
    D -->|腾讯会议录制| G["拉取转写文本"]
    E --> H["确认候选人姓名"]
    F --> H
    G --> H
    H --> I["parse_transcript 分段 → merge_turns"]
    I --> J["resolve_candidate_speaker 识别候选人说话人"]
    J --> K["pair_qa_turns 生成问答配对"]
    K --> L["规则 + 模型判定每组问答（verdict / substance / followup）"]
    L --> M["推导维度分 + 模型打分维度 → 加权总分"]
    M --> N{"证据是否充分"}
    N -->|否| O["结论强制待定 + 原因与复核提示"]
    N -->|是| P["输出推荐 / 不推荐 + 风险提示"]
    O --> Q["写入 interviews.evaluation"]
    P --> Q
    Q --> R["HR 复核 → apply_manual_scores 修订留痕"]
```

关键设计：

| 设计项 | 说明 |
| --- | --- |
| 说话人识别 | 优先按姓名标签匹配；匹配不到时用模型推断并记录 `candidate_evidence` 与 `candidate_confidence`，前端提示「未经人工确认」 |
| 问答配对 | 以面试官发言为一问、候选人连续发言为一答；无回答的组标记为「未作答」 |
| 规则唯一来源 | 三个判定字段的档位定义、推导权重、四维权重都写在规则文件里，提示词由同一文件渲染，避免「改了提示词没改代码」 |
| 判据覆盖 | `engine=rule` 的档位由代码确定性判定并覆盖模型结论；`hybrid` 先规则后模型；`llm` 只做语义分档 |
| 计分口径 | 总分只由 status=scored 的维度加权折算，缺失维度权重按比例归一；模型自报总分不采信 |
| 纠偏策略 | 有效问答不足、转写过短、配对失败、标签缺失达 20% 以上、姓名对不上说话人 → 强制待定并降置信度 |
| 人工修订 | `apply_manual_scores` 校验取值范围，重算总分，写入修订记录，保留原始评价 |
| 会议能力 | 会议创建/查询/取消由 `MeetingService` 统一封装；未配置 Token 时返回 503 明确提示 |

状态机：

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| `not_started` | 已建会，未上传/未转写 | 建会成功 |
| `transcribing` | 转写中 | 上传音视频或拉取录制 |
| `transcript_ready` | 逐字稿就绪，待分析 | 转写成功 |
| `analyzing` | 评分中 | 触发分析 |
| `completed` | 评价完成（可能结论为待定） | 分析成功 |
| `failed` | 失败 | 转写或分析异常，`error_message` 记录原因 |

失败处理：

| 场景 | 处理 |
| --- | --- |
| 未配置腾讯会议 Token | 返回 503「未配置 TENCENT_MEETING_TOKEN」 |
| 会议创建失败 / Token 失效 | 返回腾讯侧错误码（如 `190200`），提示重新获取 Token |
| 未安装 ffmpeg | 转写阶段返回「服务器未安装 ffmpeg，无法处理音视频」 |
| 文件超过 `INTERVIEW_MEDIA_MAX_MB` | 返回 413 并提示上限 |
| 转写结果为空 | 标记 `failed`，保留原文件，允许重新上传 |
| 转写未区分说话人 | 允许继续，但分析结果降置信度并提示核对姓名 |
| 分析超时或 LLM 失败 | 标记 `failed`，逐字稿保留，可重试分析 |

设计约束：

- 评价必须可追溯：结论 → 维度 → 问答 → 逐字稿原文，四级可下钻。
- 规则文件变更必须升 `rule_version`，历史评价保留旧版本号。
- 不允许在代码里硬编码档位文案，档位表的唯一来源是规则文件。
- 面试记录按 `user_id` 隔离，跨用户访问返回 404。

## 5. Agent 编排设计

### 5.1 设计定位

Agent 是受控工具编排层，不是无限自主执行的通用智能体。当前实现由 **LangGraph 状态图**承载：主图只做路由分发，每个意图是独立编译的子图，确认节点通过 `interrupt` 真暂停，跨轮产物由 checkpointer 持久化。相比早期「线性流程 + 提示词约束」，流程边界由图的节点与条件边保证，而不是依赖模型自觉遵守。

### 5.2 工具注册表

| 工具 | intent | 路由 | 前置条件 |
| --- | --- | --- | --- |
| JD 生成 | `jd` | `/recruitment/jd-generator` | 岗位名称、地点、薪资、经验、学历 |
| JD 修改 | `jd_edit` | `/recruitment/jd-generator` | 定位到要改的 JD、明确修改要求 |
| 评分标准修改 | `criteria_edit` | `/recruitment/resume-screening` | 定位到评分标准、明确修改要求 |
| 简历评分 | `resume_screening` | `/recruitment/resume-screening` | 简历文件、匹配 JD |
| 面试方案 | `interview_plan` | `/recruitment/smart-interview` | 已评分候选人 |
| 试卷生成 | `exam_generate` | `/training/exam-generator` | 知识库文档、试卷配置 |
| 资源删除 | `resource_delete` | 无固定路由 | 资源类型和名称/候选人/标题 |
| 邮件通知 | `email_notification` | 由 Skill 元数据决定 | 收件人、主题、内容、确认 |

说明：

- 工具注册表由 `_build_tool_registry()` 构建；`backend/skills/*/SKILL.md` 中的技能（当前为 `hr-agent-email`）会自动注册为额外工具。
- `jd_edit`、`criteria_edit`、`resource_delete` 都依赖「定位对象」这一步，定位来源优先图状态 `artifacts`，其次会话消息历史。

### 5.3 决策流程

```mermaid
sequenceDiagram
    participant User as 用户
    participant FE as HRAgent.vue
    participant API as /api/v1/agent/stream
    participant Graph as LangGraph 主图
    participant Sub as 意图子图
    participant Tool as 业务服务/Skill

    User->>FE: 输入自然语言和附件
    FE->>API: POST，带 message/attachments/conversation_id
    API->>Graph: astream(thread_id=conversation_id)
    Graph->>Graph: route_intent：构建记忆 + 规则快通道 + ReAct 决策
    Graph-->>FE: SSE progress（步骤）
    alt 普通对话
        Graph->>Sub: chat 节点（ReAct 工具循环）
        Sub-->>FE: SSE delta（文本）
    else 缺少前置条件
        Graph-->>FE: SSE final（missing_fields + suggestions）
    else 需要确认
        Graph->>Sub: 进入确认节点
        Sub-->>FE: SSE interrupt（payload + thread_id）
        User->>FE: 点击确认 / 修改
        FE->>API: POST /agent/graph/resume
        API->>Graph: 从 checkpoint 恢复
        Sub->>Tool: 执行写操作
        Tool-->>Sub: 结果与产物
    else 直接执行
        Graph->>Sub: 执行节点
        Sub->>Tool: 调用业务服务
        Tool-->>Sub: 结果与产物
    end
    Graph-->>FE: SSE artifact + final（artifacts/suggestions/route）
```

### 5.4 输出结构

Agent 输出应包含：

- `message`：给用户看的自然语言回复。
- `intent` / `route`：识别到的意图与推荐页面。
- `steps`：任务判断、工具选择、执行状态。
- `artifacts`：生成的 JD、评分结果、面试方案、试卷等产物。
- `suggestions`：下一步建议。
- `missing_fields`：缺失条件。
- `requires_confirmation`：是否等待用户确认（配合 `interrupt` 事件）。

SSE 事件契约（前端按类型渲染）：

| 事件 | 载荷 | 前端行为 |
| --- | --- | --- |
| `progress` | `node`、`steps` | 更新步骤条 |
| `delta` | `delta`、`section` | 追加流式文本到对应区块 |
| `artifact` | 产物对象 | 渲染产物卡片（可编辑/可保存） |
| `interrupt` | `thread_id`、`payload` | 渲染确认卡片，暂停等待用户 |
| `final` | `response`、`thread_id` | 结束本轮，落库消息 |
| `error` | `error` | 展示失败原因与重试入口 |

### 5.5 Agent 安全边界

- Agent 只能调用工具注册表与 Skill 目录中声明的能力。
- 路由节点只做选路，不执行任何写操作；删除、发送、落库由后续确定性链路执行。
- 需要确认的意图在图上真暂停（`interrupt`），未确认不会执行写操作。
- 删除类请求必须先在 `artifacts` 或资源查询中观察到明确目标，不允许臆造名称或 ID。
- 邮件只能生成草稿，发送必须经过人工确认。
- Agent 不应暴露模型完整内部推理，只展示一句业务判断摘要。
- Agent 输出的业务产物仍需进入页面编辑、保存或确认流程。

| Exam / Question | `exams`、`questions` | 试卷和题目 |
| ExamResult | `exam_results` | 答题结果和得分 |
| EmailConfig / EmailFetchLog | `email_configs`、`email_fetch_logs` | 邮箱配置和抓取日志 |

不在本系统建表、由远程 HR 服务持久化的对象：

| 对象 | 归属 | 本系统保留内容 |
| --- | --- | --- |
| JobDescription | 远程 `/job-descriptions/*` | 远程 ID 与产物快照 |
| ScoringCriteria | 远程 `/scoring-criteria/*` | 远程 ID 与产物快照 |
| InterviewPlan | 远程 `/interview-plans/*` | 远程 ID；发起面试时写入正文快照 |

> 早期版本曾在本系统建 `job_descriptions`、`scoring_criteria`、`interview_plans` 表，迁移后已移除；文档与代码不一致时以本表为准。

### 6.2 数据存储

- 结构化业务数据存储在 PostgreSQL。
- 文档向量存储依赖 PostgreSQL + pgvector（`documents.embedding`，维度由 `VECTOR_DIMENSION` 决定）。
- 上传原始文件与面试音视频存储在 `uploads` 目录（`UPLOAD_DIR`）。
- 对话历史和 AI 产物保存为数据库记录，便于后续查询。
- Agent 图状态（checkpoint）保存在同一数据库的 LangGraph checkpoint 表中，会话结束后仍可恢复。

### 6.3 数据生命周期

- 上传文件：上传后保存元数据，处理后生成文本切片和向量。
- JD/评分标准：生成后由用户确认保存，支持更新和删除。
- 简历评估：上传和评估后生成记录，支持状态更新和删除。
- 面试：建会后生成记录；上传材料 → 转写 → 分析 → 评价逐级写入同一条记录；删除记录时同步清理音视频文件。
- 试卷：生成后保存为试卷记录，支持分享和结果关联。
- 邮件日志：抓取和测试过程应保留日志，便于排障。

    User ||--o{ Document : uploads
    KnowledgeBase ||--o{ Document : contains

## 7. RAG 与知识库方案

### 7.1 文档处理

1. 用户上传 PDF、Word、TXT 等资料。
2. 后端校验文件大小和格式。
3. 文档服务提取文本。
4. 文本切片。
5. Embedding 服务生成向量。
6. 写入 pgvector。

### 7.2 查询流程

1. 用户输入问题，可选择知识库，也可不选（全库检索）。
2. `KBSelectionService` 按问题内容匹配最相关的文档/知识库，并给出置信度。
3. 开启查询增强时（`KB_QUERY_ENHANCE_ENABLED`）做查询改写与扩展（`KB_QUERY_EXPANSION_MAX_TERMS`）。
4. 进行向量召回与文本匹配，按 `RAG_TEXT_WEIGHT` / `RAG_CONTENT_WEIGHT` 融合排序。
5. 低于 `RAG_MIN_SIMILARITY_SCORE` 的候选被丢弃。
6. Rerank 服务重排候选上下文（`RERANK_TOP_K` / `RERANK_FINAL_K`）。
7. 将上下文交给 LLM 生成回答。
8. 返回答案和相关文档依据。

### 7.3 质量控制

- 最低相似度阈值可配（`RAG_MIN_SIMILARITY_SCORE`）；全部低于阈值时按「资料不足」回答，不编造。
- 支持 rerank 开关和 top-k / final-k 参数；rerank 失败降级为原始召回排序。
- 未处理完成的知识库文档不参与检索。
- 删除文档时同步清理切片与向量，确保不再被检索。
- 无相关知识时提示用户，而不是强行编造答案。

## 8. 外部服务集成

| 服务 | 用途 | 配置项 |
| --- | --- | --- |
| Dify | JD（type=1）、评分标准（type=2）、简历评估（type=3）、面试方案（type=4）、试卷意图（type=5）等固定工作流 | `DIFY_BASE_URL`、`DIFY_API_KEY`、`DIFY_USER_ID` |
| LLM | 文本生成、意图判断、问答、面试评分 | `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL`；Agent 路由另用 `AGENT_ROUTER_*` |
| Embedding | 文档向量化（分批调用，避免单次超限） | `EMBEDDING_API_KEY`、`EMBEDDING_BASE_URL`、`EMBEDDING_MODEL`、`VECTOR_DIMENSION` |
| Rerank | 检索结果重排 | `QWEN_API_KEY`、`QWEN_MODEL`、`RERANK_ENABLED` |
| 腾讯会议 MCP | 面试建会、查状态、取消、拉录制转写 | `TENCENT_MEETING_TOKEN`、`TENCENT_MEETING_MCP_URL`、`TENCENT_MEETING_SKILL_VERSION` |
| DashScope ASR | 面试音视频转写 | `LLM_API_KEY`（需开通语音识别）、`DASHSCOPE_ASR_MODEL` |
| ffmpeg | 音视频抽取音频 | 系统依赖（容器镜像已内置） |
| 远程 HR 服务 | JD / 评分标准 / 面试方案持久化 | `HR_SERVICE_HOST`、`HR_SERVICE_PORT`、`HR_SERVICE_APIKEY` |
| 邮箱服务 | 邮件抓取、测试、草稿/发送能力 | EmailConfig 数据表 |

### 8.1 外部服务失败策略

| 服务 | 失败表现 | 处理策略 |
| --- | --- | --- |
| Dify | 工作流超时、返回异常、网络不可达 | 返回失败步骤，提示重试或走人工流程 |
| LLM | 内容生成失败、响应超时 | 保留用户输入，允许重新生成 |
| Embedding | 文档无法向量化 | 文档标记处理失败，允许重新处理 |
| Rerank | 重排失败 | 可降级为向量召回原始排序 |
| 腾讯会议 | Token 未配置 / 失效（`190200`）/ 账号类型不支持 | 建会返回 503 或业务错误码，提示重新获取 Token |
| ASR / ffmpeg | 未安装 ffmpeg、格式不支持、转写为空 | 面试记录标记 `failed`，保留原文件，允许重传 |
| 远程 HR 服务 | 超时（默认 30s）、返回非 2xx | 返回失败提示，不本地兜底造数据 |
| 邮箱 | 连接失败或认证失败 | 返回连接测试错误，不启动发送 |

### 8.2 配置管理

- 所有外部服务地址、模型名和密钥应通过 `.env` 或企业密钥系统注入。
- 生产环境不得使用仓库中的默认示例密钥。
- 配置变更需要记录变更人、时间和影响范围。

## 9. 权限与安全设计

### 9.1 认证

- 登录成功后签发 JWT。
- 后端通过 OAuth2 Bearer Token 获取当前用户。
- Token 载荷中包含用户 ID，并设置过期时间。
- 密码使用 bcrypt 哈希。

### 9.2 授权

- 基础接口要求 `get_current_user`。
- HR 相关接口可按需要使用 HR 角色依赖。
- 超级管理员接口使用 `get_current_superuser` 或 `get_current_admin_by_role`。
- 邮箱配置、用户管理、角色管理应仅允许超级管理员访问。

### 9.3 敏感信息

- 生产环境必须替换默认密钥、数据库密码和 API Key。
- 不允许在前端暴露 LLM、Dify、邮箱密码、腾讯会议 Token 等敏感配置。
- 上传的简历、候选人信息、面试音视频、逐字稿、考试结果应按企业数据安全要求限制访问和留存。
- 面试记录、简历评估等业务对象按 `user_id` 隔离，跨用户访问返回 404。

### 9.4 安全控制点

| 控制点 | 设计 |
| --- | --- |
| 登录认证 | JWT Bearer Token |
| 密码保存 | bcrypt 哈希 |
| 管理接口 | 超级管理员依赖校验 |
| 邮箱配置 | 仅超级管理员访问 |
| 文件上传 | 大小和格式限制 |
| 简历数据 | 仅授权用户访问，生产需明确保留期限 |
| 面试音视频与逐字稿 | 按人隔离访问；录音告知；明确保存期限与清理流程 |
| Agent 写操作 | 确认节点真暂停；路由不执行写操作 |
| AI 输出 | 人工确认后用于业务流程 |
| 对外通知 | 不允许绕过确认自动发送 |

## 10. 异常处理设计

### 10.1 统一错误结构

后端异常处理返回统一结构：

```json
{
  "error": {
    "message": "错误信息",
    "type": "错误类型",
    "details": {}
  }
}
```

### 10.2 主要异常场景

| 场景 | 处理方式 |
| --- | --- |
| 未登录或 Token 无效 | 返回 401 |
| 权限不足 | 返回 403 |
| 参数校验失败 | 返回 422，包含字段错误 |
| 唯一约束冲突 | 返回 409 |
| 外键引用无效 | 返回 400 |
| 资源不存在 | 返回 404 |
| 数据库异常 | 记录日志，返回可理解错误 |
| LLM/Dify 超时或失败 | 返回失败状态和重试建议 |
| 文件解析失败 | 返回文件名、失败原因和可接受格式 |

### 10.3 前端展示

- 表单错误展示字段级提示。
- 接口错误展示业务可理解提示。
- 长任务失败时展示已完成步骤和失败原因。
- 权限错误跳转或提示联系管理员。

### 10.4 日志设计

建议记录以下日志：

- 应用启动、关闭、数据库初始化。
- 登录失败、Token 校验失败、权限不足。
- 文件上传、处理、解析失败。
- Dify、LLM、Embedding、Rerank、腾讯会议调用失败。
- 面试转写、说话人识别、问答配对、评分失败与待定原因。
- Agent 工具选择、执行失败和高风险操作确认。
- 数据库完整性冲突和外键引用失败。

日志中应避免记录明文密码、完整密钥和不必要的简历敏感信息。

## 11. 部署方案

### 11.1 开发部署

- 后端：`python main.py` 或 `uvicorn main:app --reload --host 0.0.0.0 --port 8000`（入口是 `backend/main.py`）
- 前端：`npm run dev`（Vite 7，需 Node 20.19+ / 22.12+）
- 数据库：`backend/docker-compose.yml` 启动 PostgreSQL + pgvector
- 本地还需安装 `ffmpeg`（面试音视频转写依赖）

### 11.2 生产部署建议

- 前端构建为静态文件，由 Nginx 或企业 Web 服务托管。
- 后端以 Uvicorn/Gunicorn 或容器方式部署。
- 数据库使用独立 PostgreSQL 实例并启用 pgvector。
- `.env` 由运维或密钥管理系统注入。
- 上传目录需要持久化卷（含面试音视频，容量需按面试场次估算）。
- 日志需要接入企业日志平台或至少保留滚动文件。
- LLM/Dify/Embedding/Rerank/腾讯会议 MCP 服务需要网络连通性和密钥。
- 运行镜像需包含 `ffmpeg`（仓库 Dockerfile 已内置）。

### 11.3 部署拓扑

```mermaid
flowchart LR
    Browser["用户浏览器"] --> Web["Web/Nginx 静态资源"]
    Web --> Backend["FastAPI 后端服务"]
    Backend --> PG["PostgreSQL + pgvector"]
    Backend --> Upload["持久化上传目录"]
    Backend --> Dify["Dify 工作流服务"]
    Backend --> Model["LLM/Embedding/Rerank 服务"]
    Backend --> Mail["SMTP/IMAP 邮箱服务"]
    Ops["运维/日志系统"] -.-> Backend
    Ops -.-> PG
```

### 11.4 环境分层

| 环境 | 用途 | 特点 |
| --- | --- | --- |
| 开发环境 | 本地开发和调试 | 可使用本地数据库和测试 Key |
| 测试环境 | 联调和测试执行 | 数据可重置，外部服务使用测试配置 |
| UAT 环境 | 业务验收 | 尽量接近生产，使用脱敏测试数据 |
| 生产环境 | 正式试点或上线 | 密钥、备份、日志、权限必须满足上线条件 |

## 12. 可扩展设计

- 新增 HR 工具时，在 Service 层实现业务逻辑，并在 Agent 工具注册表中声明 intent、route、description、prerequisites。
- 新增 Skill 时，在 `backend/skills` 下维护 `SKILL.md`、`skill.json`、脚本和参考资料，并由 dispatcher 接入。
- 新增 Agent 意图时，在 `app/agent/nodes` 实现节点、在 `app/agent/graph.py` 注册子图、在工具注册表声明 intent 与前置条件；确认类意图用 `interrupt`。
- 调整面试评分口径时，先改 `app/rules/interview_rules_v1.json` 并升 `rule_version`，再由渲染函数同步提示词；不允许只改提示词。
- 新增页面时，在 `frontend/src/views`、`frontend/src/api` 和 router 中补齐页面、接口和菜单。
- 新增数据实体时，补充 model、schema、service、endpoint；表结构由启动时 `create_all` 建表，生产变更建议补迁移脚本。

## 13. 方案评审检查点

- 架构是否覆盖全部 P0 业务流程。
- Agent 的工具边界和确认机制是否清晰，确认是否为图上的真暂停。
- 数据实体是否支撑查询、保存、删除、复用和审计。
- 面试评价是否做到「结论 → 维度 → 问答 → 原文」四级可追溯。
- 规则文件是否作为评分口径的唯一来源，历史结果是否带 `rule_version`。
- 外部 AI 服务与腾讯会议失败是否有降级或提示。
- 权限控制是否以后端校验为准，面试音视频是否按人隔离。
- 上传目录、数据库和日志是否具备生产化准备。
- 是否明确哪些能力属于项目内实现，哪些依赖企业平台。
