## backend 架构梳理（LangGraph vs Dify）
- 结论：两者分层协作，不是替代关系。LangGraph 是本地编排/控制面（意图路由、状态机、人机确认、SSE），Dify 是远端内容生成/执行面（6 类 HR 生成工作流）。
- LangGraph：`app/agent/graph.py` 主图 START→route_intent→条件边→独立编译意图子图；`checkpoint.py` AsyncPostgresSaver（thread_id=conversation_id）；`nodes/jd.py` interrupt 确认；`bridge.py` astream(updates+custom)→SSE；`routing_agent.py` 受控 ReAct 只读选路；`nodes/chat_agent.py` create_agent ReAct 循环。入口 `/agent/graph/chat`+`/resume`，`/agent/*` 文件流用 preset_intent 直通。
- Dify：`dify_service.py` 统一封装 `/v1/chat-messages`，inputs.type 分派：1=JD生成/需求解析、2=评分标准、3=简历评价、4=面试方案、5=试卷生成/意图解析、6=逐题阅卷。调用方：`hr_workflows.py`（旧表单式直连，不过图）、`chains/resources.py`、`exam_service.py`、`resume_evaluation_service.py`。
- 注意：`dify_service.py` 注释写「2=简历评价」与实际不符（实际 2=评分标准、3=简历评价），以调用点为准。Dify 的 conversation_id 与 LangGraph 的 thread_id 是两套独立会话标识。
- 不经过 Dify 的场景：chat/路由/编辑改写/邮件草稿走本地 LLM（LLM_API_KEY 直连）。

## /agent 与 /agent/graph 端点对照（含前端）
- 两者共用 `AgentGraphService` + 同一 checkpointer + 同一套 SSE 契约，区别在入口形态：`/agent/graph/*` 完整走 route_intent（规则+ReAct 选路），`/agent/*` 用 `preset_intent` 直通 exec 节点、跳过意图识别。
- 前端 `src/api/agent.js`：`graphChat/graphResume` → `/agent/graph/*`；其余 5 个 → `/agent/*`，统一由 `HRAgent.vue` 的 `consumeAgentStream` 解析。
- 触发点：`sendMessage`/`sendSuggestion`/附件对话/邮件确认(`confirmAndSendEmail`) → graphChat(1053)；JD 确认 `confirmAndGenerate` → `streamAgent({useResume:true})` → graphResume(1451)，thread_id 丢失则降级 `agentApi.stream`(1452)。
- 面板按钮 → /agent/*：`startResumeScreening`(313)→resume-screen/stream；`startInterviewPlan`(340)→interview-plan/stream；`startExamGeneration`(410)→exam/document-stream（有文档）或 exam/stream。
- 细节：前端未单独处理 `interrupt` 事件，靠 `final.requires_confirmation && intent==='jd'`(1144) 弹确认框；`agentThreadId` 从 SSE `event.thread_id` 取(1059/1935)；`startNewConversation`/`switchConversation` 未重置 agentThreadId，属潜在边缘 bug。
- 用户贴的 `prefix=" /agent"` 带前导空格，实际 api.py 是 `"/agent"`，无此问题。

## core.py / _AgentServiceCoreMixin 结构
- 继承：`AgentService(_AgentServiceCoreMixin, _AgentServiceEditingMixin, _AgentServiceResourcesMixin)`，MRO Core→Editing→Resources；三者都无 `__init__`、无状态，只有 AgentService.__init__ 提供 db/tool_registry/skill_dispatcher/email_send_service 及懒加载 llm_service/dify_service。mixin 间互相调用（core 调 resources 的 `_generate_jd`/`_save_*`、editing 的 `_resolve_interview_exam_followup`），属逻辑拆分非解耦；core.py 无 LangGraph import，图节点经 configurable 取 service 调其方法。
- 六组能力：①工具/技能注册与附件规范化；②JD 非流式生成链 `_run_recruitment_agent`（jd.py:111 非流式路径用）；③邮件 skill 草稿/发送（skill.py 两节点）；④SSE 事件构造器（`_stream_event` 硬编码 jd 为历史遗留，新码用 `_tool_stream_event`）；⑤试卷流式 + 补题 + `***`/`|` 六字段转 Markdown + 面试方案 8:2 出题上下文；⑥记忆/指代解析 + 60 分阈值评分→面试/删除闭环。
- 关键调用点：`_route_for_intent`→routing.py:54；`_normalize_attachments`→bridge.py；`_filter_attachments`/`_normalize_memory_text`/followup 规则→reasoning.py 快通道；`_build_memory_augmented_prompt`→legacy.chat_node 兜底；`_resolve_interview_candidate`→agent_service.py:223；`_build_resume_screening_followup_response`→_handle_interview_plan_chat:216 与 nodes/resources.py:70；`_generate_exam_*`/`_drain_exam_display_buffer`→stream_exam_generation:885-917。
- 业务闭环 artifact：匹配唯一高分候选人时产出 `interview_plan_execute`，前端 HRAgent.vue:1066 自动接 `startInterviewPlan`；低分删除只给 `delete_resource_candidates` 候选清单，要求用户二次确认，不自动删。

## /chat 端点定位（补充）
- `/chat`（endpoints/chat.py，4 个端点 send/stream/suggestions/feedback）是早期通用聊天，走 `ChatService → LLMService` 单轮问答，不接 LangGraph、无意图/工具编排；`/chat/stream` 是 `text/plain` 裸文本块，不是结构化 SSE 事件。
- **当前前端完全没有调用它**：`src/api` 无 chat 模块，src 与 dist 中均无 `/chat/(send|stream|suggestions|feedback)` 字面量；后端也只有 chat.py 自身引用 ChatService。属遗留/兼容保留接口，仅 docs（06-API接口清单 17.3、05-方案设计文档）还列着。
- 前端真正的对话入口只有 `HRAgent.vue`（路由 `/agent`）→ `/agent/graph/chat`；知识问答页 `/assistant/qa` 走 `/knowledge-assistant/ask`，工作台快捷指令走 `/intent/route`；独立业务页（JD/简历/面试/试卷）走各自 REST（`/hr-workflows/*`、`/resume-evaluation/*`、`/exam-management/*` 等），均不碰这三组。

## chains/editing.py（_AgentServiceEditingMixin）梳理
- 继承：`AgentService(core, editing, resources)`，三个 Mixin 无继承关系，靠 `self._xxx` 跨文件互调；editing.py 自身依赖 core.py（`_format_memory_for_prompt`、`_normalize_candidate_match_text`、`_is_followup_interview_exam_request`）与 resources.py（`_safe_json_loads`、`_clean_optional_value`、`_is_generic_*_edit_request`、`_is_*_edit_followup`、`_recent_generated_resources`、`_list_deletable_resources`、`_match_delete_resources` 等）。实例经 `configurable.agent_service` 注入节点。
- 意图：`reasoning.classify_agent_intent`(101-104) + `build_rule_agent_plan`(141-156) 用 `_is_jd_edit_request`/`_is_criteria_edit_request`(resources.py:1022/1035) 走规则快通道 → dest_node=jd_edit/criteria_edit。`graph.py:75-94` 编译 4 节点子图 parse→locate→rewrite→save，`end_after={locate,rewrite,save}`。
- **编辑链路的确认不是 interrupt**：locate 无候选/多候选/缺 changes 时写 `final_response` 提前 END，靠 artifact（`jd_edit_request`/`criteria_edit_request`/`*_edit_candidates`）+ `memory_context` + `_recent_pending_*` 反查 `Message.context.agent_response` 做下一轮续接。所以依赖前端把 agent_response 持久化；与 JD 生成的 `jd_confirm` checkpointer interrupt → `/agent/graph/resume` 是两套机制。
- 改写走**本地 LLMService**（`_rewrite_*_content`），不走 Dify；`_build_*_update_payload` 保留原记录其余字段并写 meta_data 的 `last_edit_source`/`edit_history`（最近 10 条）。
- 潜在不一致：评分标准只重写 `content`，`criteria_data`/`total_score`/`scoring_dimensions` 保留原值——「技能匹配改成 40 分」不会同步到结构化分值；JD 的结构化字段虽写回顶层+meta_data，但正文由 LLM 重写，两处可能不一致。
- `_resolve_interview_exam_followup`(编辑文件内但服务于试卷) 由 `core.py:688 _hydrate_exam_interview_context` 调用，把最近面试方案正文注入 → `_build_exam_special_requirements` 生成 8:2（文档题:面试能力题）出题配比。`tools/router_tools.py:45-49` 的 `search_resources` 复用两个 `_resolve_recent_*_candidates` 做指代消解。
- 前端：route 常量为 `/recruitment/jd-generator`、`/recruitment/resume-screening`；HRAgent.vue 2671-2693/2712-2713/2741-2742 对编辑类 artifact 做了等待态与意图标签处理。

## chains/core.py（_AgentServiceCoreMixin）梳理
- 1143 行 / 43 个方法，是三个 Mixin 中被外部依赖最多的「运行时基座 + 流式业务执行工具箱」。四层：①启动注册 `_build_tool_registry`(7 个 AgentToolSpec + Skill bundle，按 intent 建索引)、`_build_skill_dispatcher`、`_route_for_intent`(nodes/routing.py:54 用它出 response.route)；②路由上下文 `_normalize_attachments`(bridge.py:69/134)、`_filter_attachments`(reasoning.py:110 判简历 vs 文档)、`_format_memory_for_prompt`/`_build_memory_augmented_prompt`、`_planning_step`(jd/editing/resources 节点共用)、`_is_followup_*` 追问规则、`_normalize_candidate_match_text`；③业务执行 `_run_recruitment_agent`(nodes/jd.py:111)、Skill 邮件链 `_stream_skill_draft_response`/`_handle_skill_intent`/`_build_skill_response`、试卷流式+补题+题目 Markdown 格式化、简历评分结果/60分闭环、面试候选人 LLM 解析；④输出 `_stream_event`/`_tool_stream_event`/`_resume_stream_event` + `_stream_text` 兜底。
- **迁移关键**：LangGraph 只重写了路由与状态机，业务执行未重写。`agent_service.py` 的 5 个 `stream_*`(463/599/771/850/956) 仍是执行主体，`nodes/jd.py:100`、`nodes/skill.py:34`、`nodes/files.py:34-72` 通过 `nodes/legacy.py:_emit_generator` 复用旧生成器，事件经 `get_stream_writer` 冒泡成 SSE。core.py 的事件构造器因此仍是 SSE 契约的实际来源之一。
- 两套确认之外还有第三套：JD=checkpointer interrupt；Skill 邮件=`_build_skill_response:403` 的 `requires_confirmation`/`missing_fields` + 前端回传；编辑链路=final_response + artifact 反问（见上节）。
- 坑：`_stream_event`(407) 硬编码 intent="jd"、route="/recruitment/jd-generator"，只适用 JD 链，通用要用 `_tool_stream_event`；`bridge.py:34` 重复实现了一份模块级 `_stream_text`；`_missing_exam_question_scores` 直接调 `ExamService._allocate_question_scores` 私有方法。mixin 间是双向依赖（core 也调 resources 的 `_clean_optional_value`/`_safe_json_loads`），不是严格分层。
